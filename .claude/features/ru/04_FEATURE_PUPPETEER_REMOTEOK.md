# FEATURE: Puppeteer RemoteOK Crawl Strategy (Increment 4)

*Перевод на русский для презентации. Исходник: [английская версия](../04_FEATURE_PUPPETEER_REMOTEOK.md).*

## Обзор

Добавляет вторую реальную `CrawlStrategy` в краулер: `remoteok`, которая, согласно таблице Data
Sources в `CLAUDE.md`, является `DYNAMIC`, поскольку обычный (не браузерный) запрос получает
403, выданный Cloudflare — что снова подтверждено спайком этого инкремента. Puppeteer нужен не
просто для выполнения JS, а для того, чтобы выглядеть как настоящий браузер и вообще пройти через
защиту от ботов.

Опирается напрямую на абстракцию `CrawlStrategy` из `02_FEATURE_REAL_CRAWLER_REDIS_ES.md` /
`02b_FEATURE_VACANCY_DETAIL_CRAWL.md`. `crawlRunner.ts` **не потребовал изменений** — он уже был
агностичен к конкретной стратегии (вызывает `strategy.crawl()`, делает upsert, затем опционально
`strategy.enrichDetails()`). Это подтверждает, что абстракция из Increment 2/2.2 действительно
обобщается на второй, структурно иной источник без модификаций.

Этот инкремент также переименовал существующий файл стратегии habr_career
(`axiosCheerioStrategy.ts` → `habrCareerStrategy.ts`) — см. "Decisions locked with the user" ниже.

## Статус

**Реализовано и вручную проверено** (2026-08-08). Запущены реальные краулинги обоих источников
через настоящий API (`POST /sources/:id/crawl`) против живого стека Postgres/Redis/Elasticsearch:

- RemoteOK: `RUNNING` → `COMPLETED`, найдено 50 вакансий, проиндексированы в Elasticsearch с
  чистым текстовым `description`, дедуплицированным `skillsSummary`, `isRemote: true`.
- `habr_career`: листинговый краулинг + `enrichDetails` оба по-прежнему корректно работают после
  переименования и после извлечения общего хелпера `htmlToText` (см. ниже) — подтверждено через
  вывод логов в реальном времени, затем прогон остановлен рано (в середине `enrichDetails`),
  вместо того чтобы дать завершиться полному прогону из 25 вакансий/12с задержки, поскольку
  проверка на регрессию не требовала полного прогона.
- `WeWorkRemotely`: по-прежнему корректно логирует `WARN` ("crawling not yet implemented for
  WeWorkRemotely") и завершается с 0 вакансиями, подтверждая, что рефакторинг диспетчеризации не
  нарушил путь для отложенных источников.
- Frontend: через `grep` подтверждено, что `apps/web` рендерит `skillsSummary` как непрозрачную
  строку (`entities/vacancy/ui/vacancy-card.tsx`) без каких-либо допущений о её форме через
  regex/парсинг — изменения фронтенда не требуются.

## Решения, зафиксированные с пользователем

- **Поле зарплаты: отложено**, не входит в этот инкремент — без изменения схемы ES, без
  повышения `CRAWLER_RESULTS_SCHEMA_VERSION`, без пересборки индекса. (Спайк ниже дополнительно
  подтверждает, что это было правильное решение: поле `baseSalary` в JSON-LD у RemoteOK оказалось
  нереальным шаблонным значением — см. Spike Findings.)
- **Именование файлов: по сайту, не по библиотеке.** Переименован
  `axiosCheerioStrategy.ts` → `habrCareerStrategy.ts`; новый файл — `remoteOkStrategy.ts`.
  Обоснование: старое имя описывало *технологию* (axios+cheerio), но содержимое файла (селекторы,
  парсинг JSON-LD) на 100% специфично для habr_career, а `getStrategy()` уже диспетчеризирует по
  `source.name` — стратегия концептуально соответствует 1:1 *сайту*, а не библиотеке. С одним
  файлом это было приемлемо, но становилось бы только более запутанным (`белиберда`) по мере
  добавления новых источников/технологий. Новая конвенция: `<siteKeyCamelCase>Strategy.ts`,
  соответствующая колонке `Key` в таблице Data Sources в CLAUDE.md. Библиотека
  загрузки/парсинга остаётся внутренней деталью реализации, задокументированной в шапке-комментарии
  каждого файла.
- **Новая зависимость**: `puppeteer` (полный пакет, включает Chromium) — `puppeteer-core` не
  оправдывал дополнительную сложность управления Chromium ради одного источника в MVP-демо.
- **Работает на хосте, не в Docker.** У API сегодня нет `Dockerfile`; в контейнерах работают
  только Postgres/Redis/ES. Встроенному в Puppeteer Chromium просто нужно запуститься на
  машине разработки. Контейнеризация API в будущем потребует дополнительных OS-зависимостей
  Chromium в этом образе — отмечено как будущая забота, здесь не решается.
- **User-Agent**: реалистичная строка desktop Chrome UA, не значение Puppeteer по умолчанию и не
  какая-либо идентифицирующая бота строка. `robots.txt` содержит управляемый Cloudflare раздел,
  который явно блокирует `ClaudeBot` (среди других AI/SEO-краулеров) для общего краулинга, затем
  отдельный раздел заново разрешает тех же ботов специально для использования в AI-справке/
  обучении — ни одна из этих категорий не применима к этому приложению (оно строит поисковый
  индекс по вакансиям, а не занимается AI-обучением/справкой), а честное представление
  non-browser UA свело бы на нет весь смысл использования здесь Puppeteer.
- **Диспетчеризация остаётся основанной на имени**, а не на типе (`STATIC`/`DYNAMIC`).
  `source.type` не имеет других потребителей в кодовой базе, кроме отображаемого текста; привязка
  диспетчеризации к нему неверно подразумевала бы, что "каждый источник `DYNAMIC` использует одну
  общую Puppeteer-стратегию". `getStrategy()` теперь является `Record<string, CrawlStrategy>`,
  ключом к которому служит `source.name`, что чисто композируется для будущей третьей стратегии.
- **Без `enrichDetails`** — подтверждено спайком как ненужное (см. ниже): сама страница листинга
  уже несёт всё, что несла бы детальная страница.
- **Теги навыков**: объединяются в уже существующее строковое поле `skillsSummary` (через
  запятую), а не в новое поле-массив/вложенное поле — переиспользует то, что уже есть, избегает
  повышения версии схемы, что согласуется с отложенным полем зарплаты и удерживает этот инкремент
  сфокусированным на механике краулинга.
- **Извлечён общий хелпер `htmlToText`** (`apps/api/src/crawler/htmlToText.ts`): обеим стратегиям
  нужно превращать HTML-содержащее поле `description` из JSON-LD в обычный текст с сохранением
  переносов строк. Раньше это была встроенная/дублированная логика в `habrCareerStrategy.ts`;
  извлечение её в момент, когда `remoteOkStrategy.ts` потребовал идентичного преобразования,
  избавило от дублирования настоящего алгоритма (а не просто похожего по форме кода) —
  подтверждено идентичное поведение для habr_career через ручную повторную проверку после
  извлечения.

## Результаты спайка (2026-08-08, на реальном сайте)

Перед написанием кода парсера был запущен Puppeteer против реальных страниц `remoteok.com`, чтобы
подтвердить или опровергнуть предположения — по прецеденту спайка из `02b`, поскольку вслепую
угадывать селекторы на более сложном сайте, чем habr_career, означало бы просто повторить в
обратную сторону тот же изначальный промах, что был в том документе.

- **`robots.txt`**: `Crawl-delay: 1`, `Allow: /`, запрещает только AJAX (`?action=get_jobs`),
  трекинг и пути со спам-паттернами — ничто из этого не блокирует обычный листинговый краулинг.
- **Обычный fetch → подтверждён 403**: обычный (не браузерный) запрос к `/remote-dev-jobs`
  вернул HTTP 403. Навигация Puppeteer с выбранным desktop-Chrome UA вернула 200 с реальным
  содержимым — подтверждает теорию защиты от ботов, а не просто её предполагает.
- **Страница листинга (`/remote-dev-jobs`) уже содержит всё необходимое**: каждая строка `tr.job`
  несёт собственные атрибуты `data-id`, `data-company`, `data-href`, `data-epoch` (временная
  метка публикации), видимый заголовок `h2`, колонку тегов, *а также* собственный встроенный блок
  `<script type="application/ld+json">` с полным `JobPosting` по schema.org (`description`,
  `baseSalary`, `jobLocationType`, `jobLocation` и т.д.) — запрос детальной страницы вообще не
  нужен. `enrichDetails` просто опущен.
- **Парсинг JSON-LD ненадёжен, DOM-атрибуты — надёжны**: примерно 1 из 4 выбранных строк имела
  некорректный блок JSON-LD (неэкранированные символы из описания просачивались в JSON), что
  вызывало исключение при `JSON.parse`. `externalId`/`title`/`company`/`url`/`postedAt` — все
  берутся из атрибутов `data-*` строки и текста DOM (всегда присутствуют, всегда парсятся), в то
  время как `description` рассматривается как опциональное бонусное обогащение из JSON-LD, если
  тот успешно парсится — сбой парсинга просто означает `description: null` для этой вакансии, а не
  пропущенную/провалившуюся строку.
- **Поля `baseSalary` и местоположения — шаблонные, не реальные данные**: выборка из 50 строк на
  двух разных загрузках страницы — каждая строка без исключения имела *абсолютно одинаковое*
  значение `baseSalary` (`minValue: 80000, maxValue: 150000, currency: USD`), в том числе на явно
  неинженерных, низкокачественных объявлениях ("Wholesale", "Page Not Found", "Open Vacancies").
  `jobLocationType` (`"TELECOMMUTE"`) и `jobLocation` (`"Anywhere"`) были аналогично одинаковыми в
  каждой строке. Это шаблонный filler в стиле schema.org, который RemoteOK выдаёт для индексации
  Google Jobs, а не реальная цифра по конкретному работодателю — та же закономерность, что
  CLAUDE.md уже документирует для отброшенного поля зарплаты у habr_career. Не сохраняется.
  `isRemote` вместо этого захардкожен как `true` в стратегии: это истинное утверждение о RemoteOK
  как о доске вакансий со 100% удалённой работой, а не догадка, выведенная из ненадёжной константы
  в JSON-LD построчно.
- **На этом эндпоинте нет настоящей пагинации**: `/remote-dev-jobs?page=2` вернул *идентичные* 50
  id вакансий, что и страница 1 (подтверждено прямым сравнением) — здесь нет пагинации через
  query-строку, а настоящий поток "load more" у RemoteOK идёт через AJAX-эндпоинт
  `?action=get_jobs`, который `robots.txt` явно запрещает. Поэтому `crawl()` переходит на страницу
  листинга ровно один раз за прогон независимо от `source.maxPagesToCrawl` — задокументировано в
  файле стратегии, а не молча проигнорировано.
- **Теги рендерятся дважды на строку** (варианты разметки для desktop и mobile одной и той же
  строки) — построитель `skillsSummary` дедуплицирует через `Set` перед объединением, иначе
  получилось бы `"React, React, Node, Node, ..."`.

## Изменения модели данных

Отсутствуют. `RawVacancy`, `upsertVacancy` и маппинг Elasticsearch не изменены — `crawl()` у
RemoteOK возвращает ту же форму, что и у habr_career, используя только уже существующие поля
(`description`/`isRemote`/`skillsSummary` — все уже опциональные поля в `RawVacancy`).

## Риск: rate limiting / бан IP в процессе разработки

Собственный `robots.txt` RemoteOK указывает `Crawl-delay: 1`, но засеянный `defaultDelayMs`
составляет `11000` (11с) — уже значительно более консервативно. Во время спайка итерации в
основном проводились против свежих навигаций Puppeteer, а не против кэша страниц в Redis (нужно
было видеть реальную структуру DOM каждый раз), но выборка оставалась небольшой (горстка
навигаций в сумме), а не циклом. Ни 403, ни CAPTCHA во время разработки не встретилось. Дальнейшая
доработка логики парсинга в `remoteOkStrategy.ts` должна по возможности предпочитать
существующий кэш страниц (`getOrFetch`, TTL 1 час) живым повторным запросам.
