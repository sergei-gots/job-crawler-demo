# FEATURE: Регрессионные тесты краулера + CI (Increment 5)

*Перевод на русский для презентации. Исходник: [английская версия](../05_FEATURE_CRAWLER_REGRESSION_TESTS_CI.md).*

## Обзор

В Increment 4 появилась вторая, структурно отличная `CrawlStrategy` (Puppeteer/RemoteOK) поверх
первой (Axios+Cheerio/habr_career), и при честном разборе проекта стало ясно, что самый заметный
пробел таков: каждое решение по парсингу до сих пор проверялось вручную на живом сайте или через
разовые spike-проверки — реальная проверка, но не *повторяемая*. Если разметка любого из сайтов
изменится, или будущее изменение парсера внесёт баг, ничего это не поймает — кроме человека,
который спустя несколько дней заметит, что количество вакансий выглядит неправильно.

**Цель**: добавить регрессионное покрытие для тех частей краулера, которые одновременно наиболее
хрупкие (парсинг, зависящий от разметки сайта) и наиболее дёшевы для изолированного тестирования
(чистые функции, без сети/БД), в соответствии с Testing Philosophy из CLAUDE.md ("ручное
тестирование — основной способ; автоматические тесты добавляются позже для критичных путей").
Затем настроить CI так, чтобы эти тесты действительно запускались при каждом push/PR — набор
тестов, который никто не запускает автоматически, не является регрессионной защитой.

## Статус

**Реализовано и проверено** (2026-08-08). `npm run test`/`lint`/`typecheck` — все проходят из
корня репозитория через `--workspace apps/api` (та же форма вызова, что использует CI), запущены
дважды подряд с идентичными результатами (27 тестов, 6 файлов, без утечки состояния между
тестами). Подтверждено, что `prisma generate` (необходим для сгенерированных типов
`@prisma/client`, от которых зависят `CrawlSource`/`RawVacancy`) работает без `.env`/`DATABASE_URL`,
так что CI не требует сервиса базы данных или секретов.

## Решения, зафиксированные с пользователем

- **CI**: `.github/workflows/ci.yml` запускает `npm ci`, `prisma:generate`, lint, typecheck и
  `vitest run` для `apps/api` при каждом push в `main` и при каждом pull request. Явно запрошено
  и подтверждено — именно это превращает новые тесты из локальной привычки по желанию в
  обязательное требование.
- **Область: логика парсинга + логика слияния полей в `upsertVacancy`, но не раннер.**
  `crawlRunner.ts` (переходы статусов, отмена, запись `CrawlLog`) уже содержал реальные баги
  раньше (документ Increment 2.2 фиксирует баг с неосвобождением слота при падении и race
  условие с устаревшим снапшотом на фронтенде) и тестировать его не менее ценно, но для
  изолированного вызова нужны мок-объекты Prisma+Redis+strategy — более крупная задача, чем
  текущий этап. Отмечено как следующий шаг, но не реализовано сейчас.
- **Никаких тестов с реальной сетью или реальным Puppeteer.** Все новые тесты выполняются на
  небольших вручную собранных HTML-фикстурах — тестирование против реальных сайтов было бы
  медленным, нестабильным и представляло бы собой именно тот паттерн повторяющихся внешних
  запросов, которого проект старательно избегал.
- **Минимальный рефакторинг ради тестируемости, без изменения поведения**: `parseHabrCareerPage` и
  `parseHabrVacancyDetail` (в `habrCareerStrategy.ts`), а также `parseListingPage` (в
  `remoteOkStrategy.ts`) были приватными для модуля; теперь они `export`-ируются, чтобы тесты
  вызывали их напрямую вместо мокирования `axios`/`puppeteer` только ради доступа к чистой логике
  парсинга.

## План реализации

1. `apps/api/src/crawler/htmlToText.test.ts` — уже экспортированная чистая функция, рефакторинг не
   нужен. Покрывает передачу простого текста без изменений, `<br>`→перенос строки, закрытие
   блочного тега→перенос строки, схлопывание 3+ переносов строк подряд, пустая
   строка/пробелы→`null`.
2. `apps/api/src/crawler/strategies/habrCareerStrategy.ts` — экспортированы `parseHabrCareerPage` и
   `parseHabrVacancyDetail`. Новые фикстуры в `strategies/__fixtures__/`:
   `habrCareerListing.html` (обычная карточка плюс одна с отсутствующей ссылкой/названием вакансии,
   чтобы проверить защитную проверку пропуска), `habrCareerVacancyDetail.html` (корректно
   сформированный блок `JobPosting` JSON-LD с вводным предложением
   `"Навыки: ... Квалификация: ... Специализации: ..."`),
   `habrCareerVacancyDetailNoJobPosting.html` (отсутствует парсируемый блок JobPosting — для
   подтверждения задокументированного контракта "выбросить исключение и пропустить"). Новый файл
   `habrCareerStrategy.test.ts` (3 теста).
3. `apps/api/src/crawler/strategies/remoteOkStrategy.ts` — экспортирован `parseListingPage`. Новая
   фикстура `remoteOkListing.html` с четырьмя строками `tr.job`: одна чистая (корректный JSON-LD),
   одна с намеренно повреждённым блоком JSON-LD (незакрытая строка, повторяет реальный случай,
   встречавшийся примерно в 1 из 4 карточек в ходе spike-исследования Increment 4) — для
   подтверждения корректного отката к `description: null` вместо выброшенного исключения, одна с
   дублирующимися тегами в DOM (варианты desktop/mobile разметки) — для подтверждения дедупликации,
   одна без `data-id` — для проверки защитной проверки пропуска. Новый файл
   `remoteOkStrategy.test.ts` (5 тестов).
4. `apps/api/src/crawler/index.test.ts` — `getStrategy()` возвращает нужную стратегию для
   `"Habr Career"`/`"RemoteOK"` и `null` для нераспознанных названий (`"WeWorkRemotely"`,
   `"Craigslist"`) — недорогая страховка для карты диспетчеризации, отрефакторенной в Increment 4
   (3 теста).
5. `apps/api/src/search/upsertVacancy.test.ts` — следует тому же соглашению, что и
   `suggestVacancies.test.ts` (`vi.mock` с hoisted `vi.fn()`, динамический импорт после мока).
   Проверяет формат идентификатора `sourceId:externalId`, что отсутствующие детализирующие поля
   полностью опускаются (а не записываются как `null`), что явный `null` (источник действительно
   не имеет значения) сохраняется отдельно от отсутствия поля, что присутствующие поля попадают и
   в `doc`, и в `upsert`, а также что `firstSeenAt` появляется только в ветке `upsert` (5 тестов).
6. `.github/workflows/ci.yml` (новый): `actions/checkout` + `actions/setup-node` (Node 24),
   `npm ci` в корне репозитория (workspaces поднимают `node_modules` туда же),
   `npm run prisma:generate --workspace apps/api`, затем `lint`/`typecheck`/`test` таким же
   способом — всё через `--workspace apps/api` из корня, а не через `cd`. Сервисы Postgres/Redis/ES
   не используются — ничто в новом или существующем наборе тестов их не затрагивает, а
   `prisma generate` только читает `schema.prisma`, не подключаясь к базе.
7. `README.md`: новый раздел "Automated regression tests + CI — Increment 5"; в существующий
   абзац Increment 3c, где впервые упоминался `suggestVacancies.test.ts`, добавлена
   ссылка-указатель вперёд.

## Явно вне области задачи

- Тестирование оркестрации `crawlRunner.ts` (переходы статусов, отмена, запись `CrawlLog`).
- Тестирование `rateLimiter.ts`/`pageCache.ts` против реального или мокированного Redis.
- Любые тесты с реальной сетью или реальным Puppeteer.
- Расширение покрытия `queryVacancies.ts`/фасетов сверх того, что уже есть в
  `suggestVacancies.test.ts`.
- Выделенный `vitest.config.ts` — текущих настроек по умолчанию достаточно (DOM не требуется,
  Cheerio не нуждается в jsdom).
