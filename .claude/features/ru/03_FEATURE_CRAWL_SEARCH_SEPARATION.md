# FEATURE: Разделение краулинга и поиска (Increment 3)

*Перевод на русский для презентации. Исходник: [английская версия](../03_FEATURE_CRAWL_SEARCH_SEPARATION.md).*

## Обзор

Перестраивает информационную архитектуру приложения, чтобы прекратить смешивать две разные
задачи, которые сейчас объединяет сущность `CrawlerJob`, и добавляет Coveo-подобный фасетный
поиск, требуемый MVP user story #6.

**Проблема.** Сегодня `CrawlerJob` объединяет:
1. **выполнение краулинга** — какие источники запускать, статус запуска, прогресс `JobLog`; и
2. **поиск/фильтрацию** — `keywords` плюс представление получившихся вакансий.

Но `keywords` — это **фильтр Elasticsearch, применяемый во время чтения**, а не параметр
краулинга — Increment 2 закрепил, что краулинг сохраняет *всё* найденное независимо от keywords,
а keywords лишь фильтруют данные при чтении (`queryVacanciesForJob`). Таким образом `CrawlerJob`
выполняет две несвязанные задачи, а UI-страница смешивает "настройку краулинга" с "результатами
поиска".

**Решение.** Разделить по индустриальной границе между **загрузкой контента (задача
оператора/администратора)** и **поисковым опытом (задача конечного пользователя)**:
- Краулинг становится действием над **Source** (который уже владеет всем, что связано с
  краулингом: `CrawlStrategy`, rate limiter, кэш страниц, `defaultDelayMs`, `maxPagesPerRun`).
  Собранный корпус в Elasticsearch общий, единый и дедуплицированный (`sourceId:externalId`) —
  никто не краулит свою приватную копию.
- Поиск становится отдельной страницей над этим общим корпусом, с фасетами + полнотекстовым
  поиском + релевантным ранжированием.

Это крупное изменение, поэтому оно разбито на инкременты, использующие один общий документ:
- **Phase 3a** — рефакторинг: краулинг переезжает на Sources (`CrawlerJob` → `CrawlRun`), новых
  возможностей поиска пока нет.
- **Phase 3b** — новая страница Search с фасетами, построенная на корпусе, оставленном 3a.
- **Phase 3c** — автодополнение (typeahead) подсказок в поле свободного текста страницы Search,
  помогающее пользователю *сформулировать* запрос, а не замена страницы результатов.

## Решения, зафиксированные с пользователем (не пересматривать)

- **Краулинг глобальный, не привязанный к пользователю (Variant A).** Sources — это общие,
  засеянные, глобальные строки; краулинг — операция над общей инфраструктурой, поэтому действия
  краулинга/состояние запуска/логи **не** привязаны к пользователю. Любой залогиненный пользователь
  может запустить краулинг и увидеть статус/логи любого запуска. Это соответствует стандартной
  модели "загрузка данных — забота админа/оператора, корпус общий". Это **действительно** меняет
  текущую модель владения по пользователю — раздел Security Considerations в `CLAUDE.md` (сейчас
  целиком про владение `CrawlerJob` конкретным пользователем) должен быть переписан, чтобы отразить,
  что краулинг — это общая операция, защищённая только логином + rate limiter'ом на уровне
  источника (худший случай "любой пользователь может краулить" — это избыточная работа, а не
  злоупотребление, потому что rate limiter защищает источник).
- **Настоящее разделение ролей admin/user (RBAC) отложено** на возможный будущий инкремент. Пока
  документация/UI отмечают, где *будет* находиться граница admin, но краулить может любой
  залогиненный пользователь. Это удерживает рефакторинг сфокусированным, вместо того чтобы
  разрастись в проект auth/roles.
- **`CrawlerJob` → `CrawlRun`.** Сущность `CrawlerJob` (и весь её модуль + UI создания/
  редактирования/удаления) удаляется. Состояние выполнения краулинга и логи переезжают на Sources
  через облегчённую запись `CrawlRun` (см. Data model). Связка "выбрать несколько источников +
  keywords + посмотреть результаты" распадается: выбор источника становится неявным (краулится
  конкретный источник), keywords переезжают на страницу Search.
- **В этом инкременте нет CRUD источников (создание/редактирование/удаление) через UI.**
  Краулимость живёт в **коде** (специфичная под сайт `CrawlStrategy` — селекторы, разбор JSON-LD —
  диспетчеризуемая через `getStrategy`), а не в строке `CrawlSource`. Источник, созданный через UI,
  нельзя было бы краулить без поставки парсера, поэтому "Create source" была бы вводящей в
  заблуждение возможностью (это различие между конфигурацией и кодом: реальные платформы вроде
  Coveo позволяют админам создавать источники, потому что они конфигурируют *универсальный
  готовый коннектор*; у нас же — парсеры под конкретный сайт). Sources остаются
  сконфигурированными/засеянными. Точечное редактирование только операционных параметров
  (`defaultDelayMs`, `maxPagesPerRun`) выглядит разумным, но намеренно отложено, чтобы удержать
  фокус этого инкремента; `name`/`type`/`baseUrl` никогда не должны редактироваться через UI,
  поскольку `getStrategy` диспетчеризует по ним.
- **Набор фасетов (Phase 3b)**: основные фасеты **Specialization**, **Seniority level** и
  **Remote / On-site**; фасеты второго уровня — **Location** и **Company**. Все они получены из уже
  собираемых данных — новый краулинг не нужен (детали извлечения см. в Phase 3b). Разбиение
  `skillsSummary` на нормализованный массив навыков **по-прежнему вне области** (это
  интерпретация → AI Enrichment, а не разбор шаблона).
- **"Search", а не "Searches".** Единственная бессостоятельная страница поиска (запрос + фасеты,
  без сохранения). Сохранённые поиски остаются вне MVP согласно `CLAUDE.md`.

## Изменения модели данных

Postgres (`apps/api/prisma/schema.prisma`), миграция:
- **Удаляется** модель `CrawlerJob` (и связь `User.jobs`).
- **Добавляется `CrawlRun`**: `id`, `sourceId` (FK → `CrawlSource`, `onDelete: Cascade`), `status`
  (переиспользует существующий enum статуса, переименованный `JobStatus` → `CrawlStatus`),
  `startedAt`, `finishedAt DateTime?`, и небольшое поле статистики
  (`vacanciesFound Int @default(0)`). Владеет `CrawlLog[]`.
- **`JobLog` → `CrawlLog`**: та же форма (`level`, `message`, `createdAt`), но FK переезжает с
  `jobId` (CrawlerJob) на `runId` (CrawlRun). Enum `LogLevel` остаётся как есть.
- **Инвариант конкурентности**: не более одного незавершённого (`RUNNING`) `CrawlRun` на
  `sourceId`. Защита при старте — так же, как уже делает `startJob`: запись, обусловленная
  статусом, + внутрипроцессная `Map` отмены (см. runner) — только с ключом по `sourceId` вместо
  `jobId`.
- **История против последнего запуска**: строки `CrawlRun` накапливаются как история, но UI
  Sources в этом инкременте показывает только **последний запуск для каждого источника** (статус +
  логи). Полный список истории запусков вне области сейчас (таблица поддержит это позже без
  дополнительной миграции).

Elasticsearch — без изменений в Phase 3a. Phase 3b добавляет поля/маппинги (см. ниже).

## Фаза 3a — Рефакторинг: краулинг переезжает в Sources

### Backend
- **Runner** (`crawler-jobs.runner.ts` → например `crawler/crawlRunner.ts`): сигнатура меняется с
  `startCrawlerRun(jobId, sources[])` / `stopCrawlerRun(jobId)` на пооcточниковую
  `startCrawlerRun(sourceId)` / `stopCrawlerRun(sourceId)`. Переиспользуется существующая
  внутренняя логика почти дословно — тело цикла `crawlSource(...)` по источнику, `getStrategy`,
  `enrichDetails`, `upsertVacancy`, `Map` `RunState { cancelled }` и защита через
  status-conditioned `updateMany` — всё переносится; они лишь переключаются на ключ по
  run/source и пишут `CrawlLog` (по `runId`) вместо `JobLog` (по `jobId`). Краулинг одного
  источника = один `CrawlRun`.
- **Routes/controllers/services**: модуль `crawler-jobs` удаляется. В модуль **sources**
  добавляется:
  - `POST /sources/:id/crawl` (старт) и `POST /sources/:id/crawl/stop` — защищены авторизацией,
    глобальные (без проверки владения; только `requireAuth`).
  - `GET /sources/:id/run` — последний `CrawlRun` для источника, включая его `CrawlLog[]`
    (питает UI статуса + сворачиваемых логов). Переиспользуются хелперы
    `logInfo`/`logWarn`/`logError` и паттерн fire-and-forget `.catch(...)` из текущего `startJob`.
  - Сохраняется существующий `GET /sources/:id/vacancies` (уже опирается на
    `queryVacanciesForSource`).
- **Действие "запустить краулинг всех источников"**: удобный `POST /sources/crawl-all`, который
  запускает по одному прогону на каждый краулимый источник (пропуская те, для которых
  `getStrategy` возвращает `null`, с логированием WARN, как и сегодня).

### Frontend (FSD)
- **Sidebar** (`widgets/sidebar/ui/sidebar.tsx`): навигация становится
  `About / Sources / Search / Profile` (маршрут+страница `/dashboard` может остаться, но
  переименовывается в "About", либо сам маршрут переименовывается в `/about`).
- **Удаляются** виджеты `widgets/crawler-jobs`, `widgets/crawler-job-detail` и слайсы
  `features/create-crawler-job`, `features/edit-crawler-job`, `features/delete-crawler-job`,
  `features/run-crawler-job`, а также слайс `entities/crawler-job`. Части, которые стоит сохранить
  (ниже), выносятся/переносятся до удаления.
- **Страница Sources** (`widgets/sources/ui/sources-page.tsx`): каждая строка источника получает
  Start/Restart/Stop (переиспользуются паттерны `Button` secondary-варианта + `StatusBadge` +
  фиксированной ширины `w-20` из старого списка crawler-jobs) и действие "run all".
- **Страница деталей источника** (новая, `/sources/:id`): статус краулинга + Start/Stop,
  сворачиваемая панель **Execution logs** (переиспользуется соглашение уровень `CrawlLog` → цвет:
  `ERROR` → `text-destructive`, согласно `CLAUDE.md`), и список **Vacancies** — перенесённый
  целиком со старой страницы деталей crawler-job, включая поля по вакансии (значок Remote,
  локация, сводка навыков, превью описания) и переключатель **"View raw ES data"** — всё это уже
  существует и просто нуждается в переносе.
- Переиспользуется существующий паттерн опроса состояния RUNNING (`POLL_INTERVAL_MS`) для
  живого статуса/логов.

### Документация (часть PR фазы 3a)

## Фаза 3b — страница поиска с фасетами

### Решения, зафиксированные с пользователем (2026-07-31, до реализации)

- **Layout: двухколоночный, а не привычный однoколоночный `max-w-3xl` приложения.** Каждая другая
  страница (Sources, Source detail, About, login) использует одну левовыровненную колонку согласно
  UI-гайдлайнам `CLAUDE.md`. Search — первая страница, которая в это не вписывается — панель
  фасетов должна располагаться рядом с результатами, а не над ними (вариант со стеком был
  рассмотрен и отклонён: при 3 фасетах, сложенных над результатами, страница занимает почти весь
  первый экран ещё до появления хотя бы одной вакансии). **Выбрано**: более широкий контейнер
  (`max-w-5xl`/`6xl`, уточняется на глаз по факту сборки), `Card` фасетов фиксированной ширины
  слева (`Specialization` / `Seniority level` / `Remote / On-site`), список результатов справа. Это
  осознанное, локальное исключение из правила одной колонки, а не прецедент для всех будущих
  страниц — в UI-гайдлайны `CLAUDE.md` добавляется короткая заметка, фиксирующая это как исключение.
- **Фасет Remote/On-site: два чекбокса, а не один переключатель.** `☐ Remote (N)` и
  `☐ On-site (N)`, согласуется с тем, как рендерятся все остальные фасеты (группа чекбоксов со
  счётчиками по каждому бакету), а не выделенный отдельный булев контрол. Если выбраны оба (или
  ни одного) — фильтр `isRemote` не применяется.
- **Пагинация: серверная `from`/`size`, возвращающая реальный `total`** (пересмотрено 2026-08-07
  в ходе код-ревью — заменяет исходный план "получать `size: 200` и постранично разбивать на
  клиенте"). Проблема, обнаруженная при ревью: исходный план ограничивал выдачу 200 хитами, в то
  время как агрегации фасетов считали *весь* отфильтрованный набор совпадений, поэтому бакет
  фасета мог показывать счётчик больше, чем количество результатов, которые пользователь реально
  мог пролистать — несогласованность, и молчаливое усечение, как только корпус превысит 200.
  **Выбрано**: `searchVacancies` принимает `page`/`pageSize` (по умолчанию 10, ограничение ≤ 50),
  делает один ES-запрос с `from`/`size` + `track_total_hits: true` и возвращает
  `{ hits, total, facets }`. Существующий на frontend контрол Previous/Next + "Page X of N" теперь
  управляет серверной страницей вместо нарезки клиентского массива; счётчики фасетов и постраничный
  набор результатов вычисляются из одного и того же отфильтрованного набора, поэтому остаются
  согласованными. `from + size` остаётся заметно ниже дефолтного
  `index.max_result_window` ES (10 000) при `pageSize ≤ 50` — приемлемо для этого корпуса; подход
  с курсором (`search_after`) был рассмотрен и отклонён как избыточный (он ломает произвольный
  переход по страницам и не нужен на таком масштабе).
- **Карточка вакансии становится общим компонентом**, а не дублируется: карточка, которая сейчас
  инлайн находится в `source-detail-page.tsx` (заголовок/ссылка, значок Remote, компания,
  локация, postedAt, skillsSummary, превью описания, переключатель "View raw ES data"), выносится
  в `entities/vacancy/ui/`, и обе страницы — Source detail и новая Search — рендерят её оттуда. По
  правилам FSD, `entities/vacancy` — правильное место (и виджет, и фича search зависят от неё,
  никогда не наоборот).
- **Новый backend-маршрут живёт в собственном модуле `apps/api/src/vacancies/`**
  (`vacancies.routes.ts`, монтируемый на `/vacancies`, `vacancies.controller.ts`,
  `vacancies.service.ts`, оборачивающий новый построитель запросов `search/`) — повторяет форму
  существующих модулей `sources`/`admin`/`users`, вместо того чтобы прикручивать контроллер к
  `search/`, который остаётся только запросами/ES-обвязкой (без слоя Express), в соответствии со
  слоением `controllers → services → crawler/ai/search/auth` из остальной части кодовой базы,
  описанным в `CLAUDE.md`.

### Извлечение данных для фасетов (backend, без нового краулинга)
- `parseHabrVacancyDetail` расширяется, чтобы также извлекать из того же стабильного шаблонного
  предложения habr, что уже разбирается для `skillsSummary`
  (`"Навыки: … Квалификация: <Seniority>. Специализации: <Specialization>."`):
  - `specialization` — текст после `Специализации:` (например "Фронтенд разработчик"); может
    отсутствовать → `null`.
  - `seniority` — текст после `Квалификация:` (Junior/Middle/Senior); часто отсутствует → `null`.
  Это по-прежнему разбор шаблона (краулинг), а не интерпретация. Оба поля добавляются в
  `RawVacancy`, `CrawlerResultDoc` и в upsert (тот же паттерн условного spread, уже используемый
  в `upsertVacancy`).
- **Маппинг ES** (`crawlerResultsIndex.ts`): добавляются `specialization` и `seniority` как
  `keyword`; у `location` и `company` появляется суб-поле `.keyword`
  (`{ type: "text", fields: { keyword: { type: "keyword" } } }`), чтобы они были одновременно
  полнотекстово-искомыми и агрегируемыми. `isRemote` уже `boolean` (агрегируем как есть).
- **Стратегия реиндексации: обнаружение версии индекса + пересоздание-и-повторное-заполнение**
  (пересмотрено 2026-08-07 в ходе код-ревью — заменяет более ранний путь "аддитивного
  согласования" через `putMapping`). Проблема, вскрытая ревью: `putMapping` согласовывает
  *маппинг*, но не бэкфиллит уже проиндексированные документы, поэтому добавление суб-полей
  `company.keyword`/`location.keyword` делало каждую ранее проиндексированную вакансию невидимой
  для фасетов/фильтров Location/Company, пока её не перекраулят заново — а старый комментарий в
  коде преувеличивал это как "согласовывает уже существующий индекс с текущей схемой".
  **Выбранный подход** (согласован с пользователем):
  - Elasticsearch трактуется как **производный кэш, а не источник истины** — каждая вакансия
    может быть получена заново повторным краулингом (`upsertVacancy` идемпотентен по
    `sourceId:externalId`).
  - `crawlerResultsIndex.ts` экспортирует `CRAWLER_RESULTS_SCHEMA_VERSION` (теперь `2`),
    впечатанную в `_meta` маппинга индекса при создании. `ensureCrawlerResultsIndex` читает
    сохранённую версию живого индекса и при несовпадении (включая ранее существовавший индекс без
    версии → `null`) **удаляет и заново создаёт индекс пустым**, логирует явный WARN/INFO и
    позволяет обычному процессу краулинга заполнить его заново. Константа увеличивается при любом
    изменении маппинга, которому не удовлетворяют уже существующие документы.
  - Пересоздание затрагивает **только ES-индекс** — история краулинга (`CrawlRun`/`CrawlLog`) и
    все остальные записи Postgres остаются нетронутыми. Это отличается от админского действия
    "Clear search data", которое также стирает историю `CrawlRun`.
  - **Миграция без простоя через alias (реиндексация в новый индекс + переключение alias)
    осознанно вне области на этом этапе** — избыточна для единственного dev/demo-инстанса поверх
    данных, которые можно перекраулить заново.

### Эндпоинт поиска
- Новый `GET /vacancies/search` (глобальный — не по источнику, не по job), параметры запроса: `q`
  (свободный текст) и выбранные значения фасетов `specialization` / `seniority` / `isRemote` /
  `location` / `company`. Строит один ES-запрос, возвращающий одновременно **хиты** и **бакеты
  фасетов**:
  - `bool`-запрос: фильтр по возрасту + фильтры `term`/`terms` для каждого выбранного фасета +
    `multi_match` по `q` на полях `title`/`company`/`description` (переиспользуется существующий
    OR-based `multi_match`; сохраняется семантика "совпадает по любому слову" и подсказка в UI).
  - **Агрегации** `terms` по каждому полю фасета (+ isRemote), возвращающие счётчики бакетов для
    UI фасетов.
  - *Известное упрощение, которое стоит отметить в PR*: правильная фасетная навигация вычисляет
    счётчики каждого фасета, исключая его собственный активный выбор (ES `post_filter` /
    отфильтрованные агрегации на фасет). MVP делает более простую версию с общим фильтром;
    отмечается как осознанное упрощение, а не баг.
- Это помещается в небольшой **модуль search** (или расширяет `apps/api/src/search/`) — это первая
  реальная часть "Coveo-подобного слоя над Elasticsearch", описанного в `CLAUDE.md`/
  `ARCHITECTURE.md`.

### Страница поиска (frontend)
- Новый `widgets/search` + маршрут `/search` + слайс `features/search-vacancies` +
  `entities/vacancy` (тип `Vacancy`, вынесенный из удалённого `entities/crawler-job`). Layout: поле
  свободного текста, боковая панель/панель фасетов (группы чекбоксов на фасет, каждая показывает
  счётчики бакетов), и список результатов (переиспользуется та же карточка вакансии, что и на
  странице Source detail — тот же компонент). Выбор фасета или ввод текста заново запрашивает и
  перерисовывает и результаты, и счётчики фасетов.

## Фаза 3c — автодополнение поиска (typeahead)

### Обзор

Свободный текст `q` в Phase 3b использует `multi_match`, который сопоставляет целые
проанализированные **токены** — поэтому частичный ввод никогда ничего не находит: набор `Je` не
находит ничего, даже если вакансия в `JetBrains` есть в корпусе (подтверждено вживую пользователем;
такое же поведение для любого другого префикса, например частичного кириллического названия
компании). Это ожидаемое поведение полнотекстового поиска, а не баг, но это неудобный край UX:
пользователь должен заранее знать точное слово, чтобы его найти. Phase 3c добавляет выпадающий
список подсказок в поле поиска, чтобы пользователь мог **обнаружить** нужный термин по мере ввода,
не меняя того, как сам поиск сопоставляет данные.

### Решения, зафиксированные с пользователем (2026-08-07, до реализации)

- **UX = выпадающий список подсказок, а не только инлайн-сопоставление по префиксу в результатах.**
  Выбор подсказки заполняет поле и запускает **существующий** поток поиска
  (`setQuery(value)` — без специального пути "поиск по подсказке"). Задача выпадающего списка —
  помочь пользователю *сформулировать* запрос; он не заменяет и не обходит страницу результатов.
- **Подсказки — это отдельные значения `title`/`company`, а не превью результатов по вакансии.**
  Каждая вакансия не предлагается отдельно — совпадение по префиксу дедуплицируется до набора
  различных совпадающих значений title и company, каждое из которых помечено, из какого поля оно
  взято (`"title"` | `"company"`), упорядоченных по тому, сколько вакансий несёт это значение
  (`doc_count`). Область — только `title` и `company` — не `description`, `location` или любое
  поле фасета. Подсказки по отдельным результатам (typeahead в стиле
  `search_as_you_type` / `bool_prefix`) были рассмотрены и явно отложены — см. Out of scope.
- **Сопоставление без учёта регистра, отображение в исходном регистре**: ввод `je` (в любом
  регистре) показывает `JetBrains`, отображаемый как `JetBrains`, а не в нижнем регистре.
- **Построено на уже установленном примитиве `combobox` из `@base-ui/react`** (`^1.6.0`,
  подтверждено наличие в `node_modules` — новая зависимость не нужна). Он поставляет встроенную
  поддержку серверно-управляемых (внешне отфильтрованных) подсказок через `items` +
  `filter={null}` (или `filteredItems`) с контролируемыми `inputValue`/`onInputValueChange` и
  `value`/`onValueChange`, плюс навигацию клавиатурой, закрытие по Escape, закрытие по клику вне
  элемента и плавающее позиционирование "из коробки" — ничего из этого сегодня не существует
  больше нигде в `apps/web` (нет ни одного предыдущего компонента Combobox/Popover/Dropdown, нет
  существующей обработки клавиатуры/клика вне элемента для переиспользования). **Проверено перед
  реализацией** с помощью одноразового спайк-маршрута (`app/spike-combobox/`, удалён после
  использования, никогда не закоммичен): он типизировался чисто относительно реально установленных
  типов, используя именно такую форму API, и рендерился на сервере с корректной ARIA-структурой
  combobox (`role="combobox"`, `aria-autocomplete="list"`) и без ошибок времени выполнения.
  Запасной вариант (самодельный `popover` + ручная обработка клавиатуры) не понадобился.
- **Выделенные суб-поля `.suggest` на `title`/`company`, отдельные от суб-полей `.keyword` из
  Phase 3b.** `company.keyword`, используемое для фасетов, должно оставаться в исходном регистре и
  точным — оно управляет значениями фильтра и отображением фасета Company. Добавление lowercase
  нормализатора прямо на него испортило бы фасет (фильтры/отображение с учётом регистра начали бы
  незаметно совпадать без учёта регистра и наоборот). Поэтому автодополнение получает собственные
  keyword-суб-поля `title.suggest`/`company.suggest` с кастомным lowercase-нормализатором,
  оставляя поля фасетов из 3b нетронутыми.
- **Изменение маппинга ⇒ ещё одно повышение версии схемы.** У `title` сегодня вообще нет
  суб-поля из keyword-семейства (`.suggest` — новое и для него тоже), поэтому изменение маппинга
  требуется в любом случае, независимо от техники реализации. `CRAWLER_RESULTS_SCHEMA_VERSION`
  переходит `2 → 3`; механизм версионированного пересоздания из Phase 3b делает всё остальное
  автоматически (удаление + пересоздание пустым при несовпадении, повторный краулинг для
  заполнения) — эта фаза не потребовала новой логики реиндексации, только повышение версии и два
  новых суб-поля.
- **Новая backend-поверхность повторяет форму существующего модуля `/vacancies/search`**:
  построитель запросов `suggestVacancies` в `apps/api/src/search/`, подключённый через
  существующий модуль `vacancies.service.ts`/`vacancies.controller.ts`/`vacancies.routes.ts`, а не
  через новый, так же как эндпоинт Phase 3b.
- **Эта фаза добавляет первые автоматизированные тесты репозитория (Vitest)** для нового
  построителя запросов `suggestVacancies`, конкретно потому, что в нём есть нетривиальная, легко
  и незаметно ломающаяся логика (приведение префикса к нижнему регистру, экранирование regex,
  дедупликация, восстановление исходного регистра через `top_hits`), которую дёшево покрыть
  unit-тестами с замоканным `esClient` и дорого проверять только ручным тестированием в браузере.
  Это не меняет Testing Philosophy из `CLAUDE.md` для остальной части приложения (ручное
  тестирование в браузере остаётся основным) — это локальное дополнение для одного участка чистой
  логики построения запросов.

### Backend

- **Маппинг** (`crawlerResultsIndex.ts`): `CRAWLER_RESULTS_SCHEMA_VERSION` повышается до `3`.
  Добавляется **настройка** индекса — кастомный нормализатор,
  `analysis.normalizer.lowercase_normalizer = { type: "custom", filter: ["lowercase"] }` —
  передаваемая вместе с `mappings` в том же вызове `indices.create`. Добавляются `title.suggest`
  (`{ type: "keyword", normalizer: "lowercase_normalizer" }`) и `company.suggest` (то же самое,
  добавляется рядом с существующим `company.keyword`).
- **Построитель запросов** (новый `src/search/suggestVacancies.ts`):
  `suggestVacancies(prefix): Promise<{ value: string; field: "title" | "company" }[]>`. Защита от
  ввода `< 2` символов после trim (возвращает `[]` без запроса к ES). Префикс приводится к нижнему
  регистру и экранируется под regex, затем выполняется один ES-запрос с `size: 0` — с фильтрацией
  по возрасту так же, как в `queryVacancies.ts` (переиспользует `staleCutoffIso`) — с двумя
  агрегациями `terms` (`title.suggest`, `company.suggest`), использующими
  `include: "<escaped-prefix>.*"` и суб-агрегацией `top_hits` (`size: 1`) для восстановления
  значения в исходном регистре для отображения. Бакеты отображаются в `{ value, field }`, с
  дедупликацией, с ограничением по небольшому размеру (~8 всего).
- **Эндпоинт**: `GET /vacancies/suggest?q=` — `getSuggest` из `vacancies.controller.ts` →
  `suggestAllVacancies` из `vacancies.service.ts` → `suggestVacancies`; маршрутизируется в
  `vacancies.routes.ts` (уже под `requireAuth` модуля).
- **Тесты**: `src/search/suggestVacancies.test.ts` (Vitest, `esClient` замокан), покрывающие
  защиту минимальной длины, форму запроса/агрегации, экранирование регулярного выражения префикса
  и отображение bucket→suggestion (дедупликация + восстановление исходного регистра).

### Frontend

- **`shared/ui/combobox.tsx`** — тонкая обёртка над частями `@base-ui/react/combobox`
  (`Root`/`Input`/`Positioner`/`Popup`/`List`/`Item`/`Empty`), стилизованная через `cn()` +
  `data-slot`, по тому же соглашению, что и `shared/ui/checkbox.tsx`. Подсказки серверно-
  управляемые, поэтому внутренняя фильтрация отключена (`filter={null}`/`filteredItems`), а
  `inputValue` контролируется.
- **`features/search-vacancies/`**: `api/suggest-vacancies.ts`, вызывающий
  `GET /vacancies/suggest` (переиспользуя `getJson` + поддержку `AbortSignal`, добавленные на
  этапе код-ревью Phase 3b); `lib/use-suggestions.ts`, повторяющий паттерн debounce +
  `AbortController` из `use-vacancy-search.ts` (более короткий debounce, ~150мс, плюс тот же
  порог `< 2` символов, что и на backend).
- **`widgets/search/ui/search-page.tsx`**: обычное поле `<Input>` свободного текста становится
  combobox, привязанным к тому же состоянию `query`/`setQuery`, которым уже владеет
  `useVacancySearch`. Выбор подсказки вызывает `setQuery(value)`; существующий эффект поиска
  перезапрашивает данные как обычно. Фасеты, пагинация и рендеринг результатов не меняются.

## Вне рамок (все инкременты)

- Сохранённые поиски (персистентные для пользователя) — явно вне MVP согласно `CLAUDE.md`.
- Admin/user RBAC — отложено; пока краулить может любой залогиненный пользователь.
- Создание/удаление источников, и даже точечное редактирование
  `defaultDelayMs`/`maxPagesPerRun`.
- Разбиение `skillsSummary` на нормализованный массив навыков; семантическое/нечёткое
  сопоставление keyword↔skill — оба относятся к AI Enrichment.
- Источники на Puppeteer (RemoteOK и т.д.) — по-прежнему post-MVP.
- **(Phase 3c)** Подсказки по отдельным результатам вакансий (typeahead в стиле
  `search_as_you_type`/`bool_prefix`) — отложено в пользу более простого списка подсказок из
  различных title/company.
- **(Phase 3c)** Нечёткие/устойчивые к опечаткам подсказки и любое ранжирование помимо сырого
  `doc_count`.
- **(Phase 3c)** Автодополнение по `description`, `location` или любому полю фасета.
- **(Phase 3c)** История недавних поисков.
