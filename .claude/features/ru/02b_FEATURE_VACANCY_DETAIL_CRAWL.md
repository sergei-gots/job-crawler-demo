# FEATURE: Vacancy Detail Crawl (Increment 2.2)

*Перевод на русский для презентации. Исходник: [английская версия](../02b_FEATURE_VACANCY_DETAIL_CRAWL.md).*

## Обзор

Опирается на `.claude/features/02_FEATURE_REAL_CRAWLER_REDIS_ES.md` (Increment 2 — реальный
листинговый краулинг `habr_career`, Redis, минимальный Elasticsearch). В том инкременте
загружалась только страница(ы) листинга, и сохранялись только `title`/`company`/`url`/
`postedAt`. Этот инкремент добавляет второй проход: для каждой вакансии, найденной в листинге,
загружается её собственная детальная страница, из которой в тот же документ Elasticsearch
подтягиваются более богатые поля.

**Цель**: после листингового краулинга вакансии `habr_career` также несут в Elasticsearch поля
`description`, `location`, `isRemote` и `skillsSummary` — взятые из собственных структурированных
данных `schema.org/JobPosting` на детальной странице, а не выведенные или интерпретированные.
AI-обогащение (реальное извлечение/нормализация навыков, суммаризация, категоризация) остаётся
вне рамок — см. раздел "Crawling vs. AI Enrichment" ниже о том, где проходит граница и почему.

## Баг после 3a: Stop может оставлять панель Vacancies с устаревшим снимком (найден и исправлен 2026-07-31)

**Симптом**: пользователь сообщил, что видит меньше обогащённых полей (отсутствует `isRemote` и
т.д.) на `/sources/:id`, чем ожидалось, у вакансии, которая (по прямой проверке в ES) на самом
деле *была* обогащена.

**Расследование** (прямые запросы к работающим контейнерам ES/Postgres, а не только чтение
кода):
- Первая гипотеза (неверная, впоследствии исправленная): предполагалось, что соответствующие два
  прогона были просто остановлены до того, как `enrichDetails` вообще успел начаться. Это было
  верно для того конкретного более раннего случая (`crawl_runs` id 50/51 — `runState.cancelled`
  переключился в true до того, как была достигнута проверка `!runState.cancelled` в
  `crawlRunner.ts:116`, так что `enrichDetails` для этих прогонов не запускался вовсе), но не то,
  что происходило при следующем воспроизведении.
- Второе воспроизведение: `CrawlLog` показывал, что `enrichDetails` работает нормально и
  доходит до вакансии 8/25 с записью "Stopped by user". Прямой поиск в ES по конкретной вакансии,
  которую пользователь скопировал (`3:1000166920`), показал, что она **была** полностью
  обогащена, при этом `lastSeenAt` **на 7 секунд позже**, чем строка лога "Stopped by user" —
  т.е. обогащение этой вакансии завершилось, просто уже после снимка страницы, который
  просматривал пользователь.
- **Первопричина**: гонка на фронтенде, а не баг краулера. `stopSourceCrawl`
  (`apps/api/src/sources/sources.service.ts:65`) синхронно переключает `CrawlRun.status` в
  `STOPPED` и немедленно возвращает управление — не дожидаясь завершения фоновой задачи
  (`executeCrawlRun`), которая уже выполняла один запрос детальной страницы (кооперативная отмена
  останавливает только *следующую* итерацию от старта, согласно решению "должен оставаться
  отзывчивым" из более ранней части этого документа — намеренно не изменено, см. ниже). Фронтенд
  (обработчик `onStopped` в `source-detail-page.tsx`) трактовал статус `STOPPED` как "полностью
  устаканившийся" и делал ровно один вызов обновления `loadVacancies()` прямо в момент этого
  перехода — что может обогнать ещё выполняющуюся запись (примерно до `source.defaultDelayMs` +
  собственная задержка запроса, например ~12-30с для `habr_career`) и пропустить её. Поскольку
  цикл опроса RUNNING (`source-detail-page.tsx`, `useEffect`, привязанный к
  `run?.status === "RUNNING"`) останавливается, как только статус выходит из `RUNNING`, больше
  ничего не перезапрашивает данные — устаревший снимок остаётся на экране до ручной перезагрузки
  страницы.

**Применённое исправление** (`apps/web/widgets/source-detail/ui/source-detail-page.tsx`): второй
`useEffect`, привязанный к `run?.status === "STOPPED"`, планирует один отложенный
повторный вызов `loadRun()` + `loadVacancies()`, с задержкой, равной
`source.defaultDelayMs + 10000`мс, который отменяется (`clearTimeout`), если статус снова
меняется раньше (например, запускается новый прогон) или компонент размонтируется. Намеренно
**не** исправлено путём заставления бэкендового `stopSourceCrawl` дожидаться (блокироваться на)
фоновой задачи перед возвратом (например, через уже существующий хелпер
`waitUntilNotCrawling`, уже используемый `clearSourceData`) — это сделало бы саму кнопку Stop
неотзывчивой на срок до ~30с, что прямо противоречило бы уже зафиксированному в разделе "Scope
decisions locked with the user" этого документа решению "действие Stop должно оставаться
отзывчивым". Исправление остаётся чисто клиентским: Stop по-прежнему возвращает управление
мгновенно, UI просто знает, что нужно проверить ещё раз, дав время дозаписаться последней
запаздывающей записи.

## Рассмотрено и отклонено: очистка ES-данных источника перед каждым перезапуском краула

Поднято пользователем в ходе расследования вышеописанного (**"должен ли перезапуск источника
сначала очищать все существующие данные этого источника в ES?"**) — рассмотрено и отклонено, не
реализовано:

- **Почему это выглядит привлекательно**: гарантировало бы отсутствие устаревших "хвостов"
  данных от предыдущего прогона.
- **Почему это неверно**: документы `CrawlerResultDoc` дедуплицируются по
  `sourceId:externalId` и накапливаются *между* прогонами по замыслу (модель данных из
  `CLAUDE.md`) — именно это позволяет видимому корпусу источника превышать то, что покрывает
  бюджет `maxPagesToCrawl` любого одного прогона (например, `habr_career` при 1 странице = 25
  вакансий за прогон сегодня). Вакансия, увиденная на странице 2 более раннего прогона, но
  отсутствующая на странице 1 бюджета страниц текущего прогона, всё ещё является реальной,
  живой вакансией — очистка при перезапуске удалила бы её только потому, что пагинация не
  показала её снова в этот раз, навсегда ограничивая видимый корпус бюджетом страниц одного
  прогона вместо того, чтобы позволить ему сходиться к полному покрытию за несколько прогонов.
- **Проблема устаревания данных, которую это пыталось бы решить, уже решена корректно, просто
  постепенно**: `queryVacanciesForSource` (`apps/api/src/search/queryVacancies.ts`) фильтрует по
  `MAX_VACANCY_AGE_DAYS` (по умолчанию 14 дней) относительно `lastSeenAt` — вакансия, которая
  перестаёт заново попадаться, сама выпадает из результатов, без принципа "всё или ничего".
- **Очистка уже доступна как явное, отдельное действие** — админ-кнопка "Clear data"
  (`clearSourceData`) — на случай, если пользователь действительно хочет сбросить источник.
  Автоочистка при каждом перезапуске сделала бы это действие избыточным и лишила бы пользователя
  возможности выбора.
- **Решение: без изменений** — перезапуск краулинга остаётся чистым upsert поверх существующего
  корпуса, как и сегодня.

## Замечание об именовании

Изначально задумывалось как "Vacancy Detail *Enrichment*" — переименовано в **"Vacancy Detail
*Crawl*"**, чтобы избежать столкновения с уже существующим в `CLAUDE.md` отдельным термином
"AI enrichment" (`MockAIEnricher` / `ClaudeEnricher`, суммаризация/извлечение навыков/
категоризация через Claude API). Этот инкремент не добавляет никакого AI — это второй, более
глубокий проход краулинга по данным, которые уже опубликовал сам источник.

## Область по источникам — только habr_career

Всё, что описано ниже (парсинг JSON-LD, конкретные доступные поля, находка "нет зарплаты"),
**специфично для разметки детальных страниц `habr_career`**. Всё это находится целиком внутри
`apps/api/src/crawler/strategies/axiosCheerioStrategy.ts`, за той же абстракцией
`CrawlStrategy`, которая уже используется для листингового краулинга. Когда будущий источник
(RemoteOK, WeWorkRemotely, Craigslist) получит собственный `CrawlStrategy`, ему понадобится
собственное исследование детальной страницы — другая структура сайта, другие доступные поля
(например, RemoteOK уже предоставляет структурированные теги навыков, согласно заметке в
`CLAUDE.md`, в отличие от предложения-резюме habr), и, возможно, вообще без шага детального
краулинга, если в листинге уже есть всё необходимое. Форма документа Elasticsearch
(`CrawlerResultDoc`) агностична к источнику и является общей; только логика извлечения
специфична для каждого источника.

## Результаты спайка (эта сессия, read-only `curl`-запросы к реальным страницам habr_career)

Загружены 8 реальных детальных страниц вакансий (`career.habr.com/vacancies/{numeric_id}`) плюс
3 страницы листинга (~150 карточек) для статистических проверок.

- **`<script type="application/ld+json">`, содержащий объект `schema.org/JobPosting`,
  присутствует на каждой протестированной детальной странице (8/8).** Это гораздо надёжнее, чем
  скрапинг произвольных CSS-классов — это та же структурированная разметка, которую habr
  предоставляет для индексации Google Jobs, маловероятно, что она сломается при редизайне
  фронтенда. Присутствующие поля: `title`, `description` (строка HTML), `identifier.value`
  (совпадает с числовым внешним id листинга), `hiringOrganization.name`, `jobLocation[].address`,
  `jobLocationType` (`"TELECOMMUTE"`, если удалённо), `employmentType`, `datePosted`,
  `validThrough`. Поля, которые schema.org поддерживает, но habr **не** заполняет: `baseSalary`,
  `skills`.
- **Зарплата практически никогда не раскрывается.** Проверено ~150 карточек листинга на 3
  страницах — **100%** показали `"Зарплата не указана"` в самом поле зарплаты. Единственное
  видимое число (`"Похожие специалисты получают 276 000 – 400 000 ₽"`) — это **рыночная оценка
  для похожих ролей**, а не заявленная работодателем зарплата для этой конкретной вакансии;
  сохранение её как `salary` искажало бы данные источника. **Решение: зарплата полностью
  исключена из области**, а не аппроксимируется по этой оценке.
- **Первое предложение `description` — стабильный, генерируемый сайтом шаблон, совпал в 8/8
  образцах:** `"Навыки: A, B, C. [Квалификация: X.] Специализации: Y."` — автоматически
  генерируется habr на основе собственных структурированных тегов работодателя, выбранных при
  публикации вакансии. Поскольку формат оказался согласованным на всей выборке, извлечение этого
  предложения считается **краулингом** (парсингом известного, сгенерированного сайтом шаблона), а
  не AI-интерпретацией свободного текста.

## Краулинг vs. AI-обогащение — граница, проведённая в этой сессии

- **Crawling (краулинг)** = извлечение того, что источник уже явно опубликовал, детерминированно,
  без интерпретации. Применимо к `description`, `location`, `isRemote` и `skillsSummary` ниже —
  все они являются либо буквальными полями, либо буквальным предложением по стабильному шаблону,
  уже присутствующим в собственных структурированных данных страницы.
- **AI Enrichment** (будущее, отдельный инкремент, согласно `MockAIEnricher`/`ClaudeEnricher` из
  `CLAUDE.md`) = всё, что требует интерпретации сверх буквального содержимого страницы: разбиение
  свободного списка через запятую `skillsSummary` на нормализованный, дедуплицированный массив
  навыков; извлечение навыков для вакансий, чей источник вообще не имеет структурированных тегов;
  семантическое/нечёткое сопоставление ключевых слов job с навыками вакансии (например,
  "Node.js" ≈ "JavaScript backend"); суммаризация; категоризация.
- `skillsSummary` хранится как **непрозрачная сырая строка**, не разбитая на массив — разбиение
  было бы первым шагом интерпретации (решением о том, что считать одним навыком, как обрабатывать
  вложенные обороты "Квалификация"/"Специализации") и намеренно оставлено для инкремента
  AI Enrichment, если он будет реализован.

## Решения по объёму, зафиксированные с пользователем

- **Добавленные поля**: `description` (обычный текст, HTML-теги удалены через
  `cheerio.load(html).text()` — не хранится и не рендерится как HTML, поскольку в UI сегодня нет
  рендерера, безопасно обрабатывающего HTML), `location` (из `jobLocation[].address`), `isRemote`
  (булево значение, `jobLocationType === "TELECOMMUTE"`), `skillsSummary` (сырое первое
  предложение `description`, только если оно совпадает с паттерном префикса `"Навыки:"`, иначе
  `null`).
- **Без поля `salary`** — см. находки спайка выше.
- **Без разбиения на массив навыков** — см. Crawling vs. AI Enrichment выше.
- **Детальные страницы проходят через существующую инфраструктуру Redis** — те же
  `waitForSlot`/`getOrFetch`, что и листинговый краулинг, с тем же ключеванием (`sourceId`, URL
  страницы). Никакого нового механизма ограничения частоты запросов или кэширования.
- **Без отдельного лимита на количество запросов детальных страниц.** В более ранних черновиках
  этого документа предлагался лимит (сначала глобальная переменная окружения
  `MAX_DETAIL_FETCHES_PER_RUN`, затем колонка `maxDetailFetchesPerRun` на уровне источника, по
  аналогии с `maxPagesPerRun`), ограничивающий, для скольких вакансий за прогон делается запрос
  детальной страницы. **Отклонено после обсуждения**: любой лимит ниже общего числа в листинге
  создаёт проблему "рваных данных" — одни и те же первые N вакансий получают детальное обогащение
  в каждом прогоне, а остальные — никогда, если не добавить настоящий механизм бэклога/скользящего
  выбора для постепенного схождения к полному покрытию. Такой механизм был признан излишней
  сложностью для MVP-демонстрации. **Итоговое решение: `enrichDetails` запрашивает каждую
  вакансию, найденную в текущем проходе листинга — без какого-либо лимита.** Объём уже ограничен
  существующим `maxPagesPerRun` (например, 3 страницы × 25 = 75 вакансий сегодня для
  `habr_career`). Запросы детальных страниц используют тот же ограничитель частоты на уровне
  источника (`rate:source:{sourceId}`, `defaultDelayMs` — засеян значением 12000мс для
  `habr_career`), так что полный прогон при `maxPagesPerRun = 3` занимает примерно
  (3 + 75) × 12с ≈ 15 минут. **Это осознанно**: пользователь явно отдал приоритет безопасности/
  вежливости краулинга (соблюдению ограничения частоты запросов источника) над скоростью прогона.
  Если позже понадобится более быстрый цикл демонстрации, рычагом является уже существующий
  `maxPagesPerRun` (уменьшить его), а не новый лимит специально для детальных страниц.
- **Ошибки на отдельной вакансии не фатальны**: если загрузка/парсинг детальной страницы
  завершились неудачей, залогировать `WARN` и перейти к следующей вакансии — соответствует уже
  существующей обработке ошибок на уровне источника в раннере.
- **Кооперативная отмена распространяется на цикл загрузки деталей**, а не только между
  источниками — действие `Stop` для job краулера должно оставаться отзывчивым даже при обогащении
  15 вакансий одна за другой.
- **Search**: `description` добавляется в существующие поля `multi_match` в
  `queryVacanciesForJob` (`["title", "company"]` → `["title", "company", "description"]`) —
  расширяет текущий фильтр по ключевым словам на уровне job, чтобы искать совпадения в теле
  вакансии, а не только в title/company. Без изменения поведения сопоставления по OR (см. ниже).
- **Семантика поля Keywords — задокументирована, не изменена.** `CrawlerJob.keywords` целиком
  передаётся в Elasticsearch `multi_match`, который по умолчанию использует семантику **OR**
  (совпадает с вакансиями, содержащими *любое* из слов, не все) — например,
  `"docker, kubernetes"` совпадает с вакансиями, упоминающими любое из слов, не обязательно оба.
  Это было верно и до этого инкремента, но становится более заметным теперь, когда `description`
  тоже участвует в поиске. Решение: **сохранить семантику OR** (более широкий охват — правильный
  выбор по умолчанию для сценария поиска работы; полноценный фасетный контроль в стиле Coveo уже
  отложен согласно `CLAUDE.md`), но **добавить подсказку в UI**, чтобы поведение не было
  сюрпризом: *"Matches any of these words in the vacancy's title, company, or description"* в виде
  небольшой строки `text-xs text-muted-foreground` под полем ввода Keywords, как в форме
  создания, так и в форме редактирования.

## Изменения модели данных

- Без изменений схемы Prisma (без новой колонки лимита — см. решение выше).
- `apps/api/src/crawler/types.ts` — `RawVacancy` получает опциональные поля:
  `description?: string | null`, `location?: string | null`, `isRemote?: boolean | null`,
  `skillsSummary?: string | null`. Стратегии, работающие только с листингом, просто опускают их
  (`undefined`).
- `apps/api/src/search/crawlerResultsIndex.ts` — маппинг получает:
  `description: { type: "text" }`, `location: { type: "text" }`, `isRemote: { type: "boolean" }`,
  `skillsSummary: { type: "text" }`.
- `apps/api/src/search/upsertVacancy.ts` — изменение сигнатуры не требуется; функция уже делает
  частичное обновление `doc` (не полную замену), так что повторный вызов на вакансию — один раз
  из листингового прохода (только существующие поля), один раз из прохода детального краулинга
  (добавление новых полей) — корректно объединяется без затрагивания `firstSeenAt`.
