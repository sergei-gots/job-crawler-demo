# Сценарий презентации Job-Crawler-Demo (10 минут)

Язык доклада: русский, технические термины — на английском (как в коде/UI). При необходимости
перевести на английский позже — структура и тайминг не меняются, меняется только текст реплик.

Слайды: [`job-crawler-demo-slides-light.html`](job-crawler-demo-slides-light.html) /
[`-dark.html`](job-crawler-demo-slides-dark.html) (7 слайдов) — либо готовые PDF рядом.

## Тезис доклада (держать в голове всё время)

> Цель — изучить возможный стек и подходы при crawling и aggregating данных.
> **Гипотеза**: существует ограниченный набор приёмов (strategies), применимый к произвольному
> множеству сайтов. **Исследование** — на примерах популярных сайтов, каждый — с реальной
> структурной проблемой. **Результат** — показать, что ограниченный набор стратегий закрывает
> основные случаи, а дальше данные проходят через единый маппинг → upsert → индексацию.

Каждый блок ниже явно привязан к одному из 4 пунктов этого тезиса.

## Подготовка перед докладом (сделать заранее, не во время доклада)

1. `docker compose up -d`, `npm run dev` — оба сервиса подняты и отвечают (`curl localhost:4000/health`).
2. **Хотя бы один полный прогон по каждому источнику уже сделан заранее** (данные в Elasticsearch
   уже есть) — нужно для содержательного Search-демо (facets, autocomplete) в блоке 4. Живой
   краулинг в кадре — это *дополнительный* прогон, не единственный источник данных для поиска.
3. Залогиненная вкладка на `/sources` — открыта заранее, чтобы не тратить время доклада на форму
   логина.
4. Проверить, что у RemoteOK **нет** активного `RUNNING`-прогона (иначе кнопка запуска
   заблокирована) — при необходимости точку остановить.
5. Держать открытой вторую вкладку на `/search` с уже готовым запросом (например `q=python`) —
   переключаться на неё, а не печатать всё в кадре.

## 0:00–0:45 — Intro (Слайд 1)

**Показываем:** слайд 1.

**Говорим:**

> Это Job-Crawler-Demo — не job board, а демонстрация инфраструктуры, которая за job board стоит:
> crawling разнородных, местами враждебных к ботам сайтов → normalization того, что они реально
> отдают → индексация для полноценного faceted search. Та же форма задачи, что в любом production
> data-ingestion pipeline.
>
> Идея доклада простая: изучить, какой стек и какие подходы реально нужны для crawling и
> aggregating данных. Рабочая гипотеза — что существует ограниченный набор приёмов, который
> закрывает crawling практически любого сайта. Проверяем это на четырёх популярных источниках.

## 0:45–1:15 — Stack (Слайд 2)

**Показываем:** слайд 2.

**Говорим:**

> Один demo, но задействован весь стек, который встречается в реальных системах: Node.js/Express/
> TypeScript на backend, Next.js с Feature-Sliced Design на frontend, Puppeteer и Axios+Cheerio для
> crawling, Postgres/Redis/Elasticsearch для хранения, JWT для auth. AI enrichment через Claude API
> — в планах, сейчас интерфейс уже заложен через `MockAIEnricher`.

## 1:15–3:00 — Гипотеза + запуск live crawl (Слайд 3 → `/sources`)

**Показываем:** слайд 3 (pipeline), затем переключаемся в браузер на `/sources`.

**Говорим (на слайде):**

> Вот что происходит при краулинге источника: сайт → CrawlStrategy → RawVacancy → upsert в
> Elasticsearch → search UI. Два выделенных этапа — это как раз то место, где применяется
> "маппинг", но в двух разных смыслах. Вернёмся к этому чуть позже.
>
> Гипотеза, которую проверяем: один и тот же интерфейс `CrawlStrategy` должен уметь закрыть
> произвольно разные сайты — без изменения самого интерфейса.

**Переключаемся в браузер, `/sources`:**

> Вот 4 источника — Habr Career, RemoteOK, WeWorkRemotely, Craigslist. У каждого — своя
> `CrawlStrategy`. Запущу прогон прямо сейчас на RemoteOK — он самый быстрый: у него нет
> отдельного detail-page прохода, только листинг.

**Действие:** кликаем на RemoteOK → **Run crawl**. Статус переходит в `RUNNING`, начинают идти
Execution logs.

> Пока он крутится в фоне — за минуту-полторы — пройдёмся по тому, что вообще отличает эти четыре
> сайта друг от друга.

## 3:00–4:30 — Разные структуры данных (Слайд 4, краулинг идёт в фоне)

**Показываем:** слайд 4. Периодически поглядываем на вкладку с логами (не переключаемся полностью).

**Говорим:**

> Это второй пункт гипотезы: данные на разных сайтах лежат в совершенно разных структурах — и
> набор приёмов должен закрывать их все.
>
> — **Habr Career** — полностью серверный рендеринг, но с двухуровневым доступом: сначала listing
> (стандартный paging), потом отдельный HTTP-запрос на detail-страницу каждой вакансии за
> дополнительными полями — там уже структурированный `schema.org/JobPosting` JSON-LD, что стабильнее,
> чем парсить CSS-классы.
>
> — **RemoteOK** — тот, что крутится сейчас — прикрыт Cloudflare, обычный HTTP-запрос получает 403.
> Здесь нужен Puppeteer с реальным browser fingerprint. Зато вся информация уже есть в JSON-LD прямо
> в листинге — detail-запрос не нужен вообще.
>
> — **WeWorkRemotely** — здесь листинг тоже через headless Puppeteer, но после первого же перехода
> на detail-страницу браузер словили по fingerprint. Решение — тот же контент отдаёт RSS-фид той же
> категории, без Puppeteer вообще, обычным Axios.
>
> — **Craigslist** — никакой защиты от ботов нет, но это generic classifieds, не только tech.
> Ограничиваем через `cat=sof` категорию, плюс fan-out по нескольким городам.
>
> То есть один и тот же интерфейс `CrawlStrategy` закрывает: static HTML, Cloudflare-gated JS, RSS,
> и multi-city fan-out — без изменения самого интерфейса.

## 4:30–5:00 — Результат live crawl

**Действие:** переключаемся на вкладку RemoteOK — статус должен быть `COMPLETED`, видно число
собранных вакансий.

**Говорим:**

> Прогон завершился — вот собранные вакансии. Гипотеза подтверждена на практике: за несколько
> секунд прогона мы получили реальные данные с сайта, защищённого от ботов, тем же самым
> абстрактным интерфейсом, что и обычный static HTML.

## 5:00–6:00 — Маппинг / унификация (Слайд 5)

**Показываем:** слайд 5.

**Говорим:**

> Третий пункт — унификация данных. Каждый сайт отдаёт свою собственную структуру полей — привести
> их к единой целевой модели `RawVacancy` это и есть mapping, в ETL-смысле этого слова: например,
> `hiringOrganization.name` у Habr превращается в наше поле `company`, `jobLocationType ===
> "TELECOMMUTE"` — в `isRemote`. Это происходит внутри каждой стратегии, ещё до того, как что-либо
> попадёт в базу.
>
> Здесь же стоит развести два значения слова "mapping" — потому что второе значение, mapping в
> смысле Elasticsearch (схема индекса, типы полей), это отдельная, уже не ETL-история — к ней
> переходим сейчас.

## 6:00–7:00 — Upsert + Elasticsearch (Слайд 6 + "View raw ES data")

**Показываем:** слайд 6.

**Говорим:**

> Вот что реально пишется в Elasticsearch одним upsert'ом. Дедупликация — по ключу
> `sourceId:externalId`, так что повторный краулинг того же источника не плодит дубли, а просто
> обновляет `lastSeenAt`. Здесь же — Elasticsearch mapping в буквальном смысле: типы полей,
> `keyword` для фасетов и агрегаций, `text` для полнотекстового поиска.
>
> Отдельный момент — версионирование схемы: `CRAWLER_RESULTS_SCHEMA_VERSION`. Поскольку
> Elasticsearch здесь — производный индекс, а не источник истины (PostgreSQL — источник истины),
> несовместимое изменение схемы не мигрируется на месте, а просто пересобирает индекс целиком из
> уже накопленных исходных данных.

**Действие (если время позволяет):** возвращаемся на вкладку Sources, у любой вакансии нажимаем
**"View raw ES data"** — показываем тот самый JSON-документ вживую.

> Вот этот же документ — можно посмотреть его прямо в UI, это ровно то, что реально лежит в
> индексе.

## 7:00–8:30 — Search live-демо (`/search`)

**Действие:** переключаемся на заранее подготовленную вкладку `/search`.

**Говорим:**

> А вот итог всей цепочки — конечный пользовательский результат. Поиск по всему собранному корпусу,
> не по одному источнику.

**Действие:** вводим свободный текст (например `python`), показываем результаты.

> Свободный текст ищет по title, company, description сразу по всем источникам.

**Действие:** включаем 1–2 facet-чекбокса (например Remote + Seniority).

> Facets — Specialization, Seniority, Remote/On-site, Location, Company — с живыми счётчиками по
> текущей выборке.

**Действие:** начинаем печатать в поле поиска (например `Je`), показываем autocomplete-подсказки.

> И autocomplete — подсказки по `title`/`company`, начинают работать от двух символов.

## 8:30–9:30 — Итог (Слайд 7)

**Показываем:** слайд 7.

**Говорим:**

> Что демо реально доказывает:
>
> Первое — один и тот же абстрактный интерфейс `CrawlStrategy` не менялся ни разу на четырёх
> структурно разных сайтах — гипотеза подтвердилась.
>
> Второе — реальные anti-bot проблемы получили реальные решения прямо по ходу разработки, не
> постфактум придуманные.
>
> Третье — поисковый слой ведёт себя как production: фасеты, автокомплит, пересобираемый индекс.
>
> Четвёртое — вежливость by design: rate-limit с jitter и кэш на каждый источник, потому что
> demo-скрапер — всё равно скрапер.
