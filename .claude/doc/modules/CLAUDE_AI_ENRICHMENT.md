# Claude API — AI-обогащение вакансий

← назад к [макро-обзору стека](../TECH_STACK_OVERVIEW.md)

**Статус: Planned, не реализовано.** В коде на момент написания этого файла (`apps/api/src/`) нет
ни `AIEnricher`/`MockAIEnricher`, ни `apps/api/src/ai/`, ни зависимости `@anthropic-ai/*` в
`package.json` — проверено (`grep -rn -iE "enrich|claude|anthropic|AIEnricher" apps/api/src`,
`find apps/api/src -iname "*ai*"`) непосредственно перед написанием этого раздела. Ниже —
разбор того, **что задумано** (по корневому `CLAUDE.md`) и **что уже готово по факту как точка
интеграции**, а не построчный разбор существующей реализации, как в остальных module-файлах — её
пока нет.

## Задуманная роль в пайплайне

Из корневого `CLAUDE.md`:

> **Claude API** — AI enrichment (summarization, skill extraction, categorization). Start with a
> `MockAIEnricher`; wire the real API (key in `.env`) in a later stage.

Идея — после того как краулер собрал сырую вакансию (заголовок, описание, компания), прогнать
описание через LLM и получить структурированное обогащение: короткое саммари, список навыков,
категорию/специализацию. Сначала — заглушка (`MockAIEnricher`, детерминированная логика без
реального вызова API, чтобы весь пайплайн можно было разрабатывать и тестировать без ключа и без
сетевых вызовов), потом — реальный `ClaudeEnricher` за интерфейсом `AIEnricher`, включаемый по
наличию ключа в `.env`.

## Где это должно подключиться уже сегодня

Сама точка интеграции в пайплайне уже существует, просто под другим именем и с другим
содержанием — важно не спутать её с будущим AI-обогащением:

→ [`crawler/types.ts`](../../../apps/api/src/crawler/types.ts) — интерфейс `CrawlStrategy`
объявляет опциональный шаг `enrichDetails` (lines 39-44) с результатом `EnrichDetailsResult`
(lines 25-27, `{ enrichedCount: number }`). Это **не** AI — это докрутка детальной HTML-страницы
вакансии обычным Cheerio-парсингом (заполнить `description`, `location`, `isRemote` и т.п. по
данным, которых нет на странице листинга). Пример реализации —
[`habrCareerStrategy.ts#L171`](../../../apps/api/src/crawler/strategies/habrCareerStrategy.ts#L171),
разобран построчно в
[AXIOS_CHEERIO_HABR_STRATEGY.md](AXIOS_CHEERIO_HABR_STRATEGY.md). `remoteOkStrategy.ts` этот шаг
намеренно не реализует — у RemoteOK всё нужное уже есть в JSON-LD листинга (см.
[PUPPETEER_REMOTEOK_STRATEGY.md](PUPPETEER_REMOTEOK_STRATEGY.md)).

→ [`crawlRunner.ts#L116-133`](../../../apps/api/src/crawler/crawlRunner.ts#L116) — после
краула сырых листингов вызывает `strategy.enrichDetails(...)`, если стратегия его определяет, и
логирует `Enriched X/Y vacancies for <source>`. Логичное место, куда в будущем встанет вызов
`AIEnricher` — либо как ещё один шаг в этой же цепочке после `enrichDetails`, либо как отдельный
шаг конвейера — архитектурно это пока не решено.

→ [`crawlerResultsIndex.ts` line 31](../../../apps/api/src/search/crawlerResultsIndex.ts#L31) —
в `CrawlerResultDoc` уже зарезервировано поле `skillsSummary?: string | null` (и соответствующий
маппинг ES-поля, line 79), под которое ничего не пишет ни одна из текущих стратегий — единственный
след будущего AI-обогащения непосредственно в схеме данных на сегодня.

## Почему `MockAIEnricher` заложен как первый шаг, а не сразу реальный API

Тот же принцип, что и `MockAIEnricher`-first в любом внешнем интеграционном слое: реальный вызов
Claude API стоит денег за токен и требует ключа — тестировать пайплайн "краул → обогащение →
индексация в ES" на каждом прогоне через реальный API было бы дорого и медленно, плюс тесты
(`.claude/features/`, регрессионные проверки краулера) не должны зависеть от сетевого вызова к
внешнему сервису и секрета в CI. Заглушка с детерминированной логикой (например: "первые N слов
описания как summary", "совпадение с фиксированным списком ключевых слов как skills") позволяет
разработать и обкатать весь путь данных (откуда поле попадает в индекс, как отображается в
Search UI) прежде чем платить за реальные вызовы модели.

## Что нужно будет решить, когда до этого дойдёт

Не решено на сегодня (нет закреплённого решения с пользователем, в отличие от остальных
разделов этого файла):

- Форма интерфейса `AIEnricher` (сигнатура метода: на входе сырая вакансия целиком или только
  `description`? На выходе — плоские поля или один объект `{ summary, skills, category }`?).
- В какой момент пайплайна вызывается — синхронно во время `crawlRunner`, или отдельным
  batch-шагом по уже проиндексированным документам (что было бы дешевле по количеству вызовов,
  если один и тот же URL встречается повторно между краулами и не менялся).
- Какая модель семейства Claude используется, обрабатывается ли rate limiting API так же, как
  для сайтов-источников (Redis, см. [REDIS_RATE_LIMIT_CACHE.md](REDIS_RATE_LIMIT_CACHE.md)), и
  что происходит с уже проиндексированной вакансией, если вызов AI Enrichment упал (сохраняется
  ли она без `skillsSummary`, или обогащение блокирует индексацию).

Когда эта часть будет реализована, этот файл нужно переписать по образцу остальных
module-файлов (см. `.claude/doc/CLAUDE.md`) — с построчным разбором `MockAIEnricher`/
`ClaudeEnricher`, реальными ссылками на строки кода и статусом "Implemented".
