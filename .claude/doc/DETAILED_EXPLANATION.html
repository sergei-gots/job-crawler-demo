Что такое ETL-mapping и как он работает в приложении?

В сценарии презентации это называется "mapping в ETL-смысле" — отдельный термин ELT в проекте не используется, речь про обычный ETL: Extract (стратегия скачивает/парсит страницу) → Transform (маппинг полей источника в общую модель) → Load (upsert в Elasticsearch).

Целевая модель

Каждый сайт-источник отдаёт вакансию в своей структуре (HTML-класс, JSON-LD, RSS...). Прежде чем что-то попадёт в базу, каждая CrawlStrategy приводит сырые данные к единой целевой модели — RawVacancy.

export interface RawVacancy {
  externalId: string;
  title: string;
  company: string | null;

  postedAt: string | null;
  sourceId: number;
  description?: string | null;
  location?: string | null;
  isRemote?: boolean | null;

}

Пример трансформации (Habr)

Файл: apps/api/src/crawler/strategies/habrCareerStrategy.ts, строки 102–131 (parseHabrVacancyDetail)

return {

Здесь jobLocationType === "TELECOMMUTE" (строковый enum сайта) превращается в булево isRemote — то есть маппинг не только переименовывает поля, но и трансформирует их значения/типы под внутреннюю модель. Похожая логика есть в каждой стратегии (remoteOkStrategy.ts, weWorkRemotelyStrategy.ts, craigslistStrategy.ts) — свой источник, но одна и та же целевая форма RawVacancy на выходе.

Два разных значения слова "mapping"

В докладе специально разводятся два разных смысла:

  1. ETL-mapping (описано выше) — превращение сырых полей сайта в RawVacancy, происходит внутри стратегии, до записи в БД.
  2. Elasticsearch mapping — это уже схема индекса (типы полей: keyword для фасетов, text для полнотекстового поиска), см. apps/api/src/search и skill elasticsearch-conventions. Это про то, как Elasticsearch хранит и индексирует уже смапленные данные, а не про трансформацию значений.

Что такое JSON-LD и RSS — и как устроен crawling через RSS? Чем это отличается от HTML/JS-краулинга?

JSON-LD

JSON-LD (JSON for Linking Data) — формат структурированных данных, который сайты встраивают прямо в HTML-страницу для поисковиков (Google и др.), обычно по стандарту schema.org: 

<script type="application/ld+json">
  { "@type": "JobPosting", "title": "...", "jobLocationType": "TELECOMMUTE", ... }
</script>

Никакого отдельного запроса не нужно: страница пришла обычным HTML-ответом, вы просто вытаскиваете этот <script> через cheerio-селектор и парсите его как JSON, а не через CSS-классы разметки.

Файл: apps/api/src/crawler/strategies/habrCareerStrategy.ts, строки 63–69 (findJobPosting)

function findJobPosting($: ReturnType<typeof cheerio.load>): HabrJobPosting | null {
  for (const el of $('script[type="application/ld+json"]').toArray()) {
    const raw = $(el).text();
    const parsed = JSON.parse(raw) as HabrJobPosting;
    if (parsed["@type"] === "JobPosting") return parsed;
  }
  return null;
}

Почему это ценно для краулинга: структурированный JSON стабильнее, чем парсинг CSS-классов — вёрстка сайта может поменяться (редизайн), а schema.org/JobPosting-разметка обычно нет, потому что от неё зависит SEO (Search Engine Optimization — оптимизация под поисковые системы)/индексация в Google Jobs.

RSS

RSS — XML-формат ленты обновлений (<item> с <title>, <link>, <description>, <pubDate> и т.п.), исторически придуман для читалок новостей/блогов. У WeWorkRemotely для каждой категории есть RSS-фид по тому же URL, что и HTML-листинг, только с .rss на конце.

Файл: apps/api/src/crawler/strategies/weWorkRemotelyStrategy.ts, строки 280–289 (enrichDetails)

const rssUrl = `${listingUrl(source, listing)}.rss`;
const response = await axios.get<string>(rssUrl, {
  headers: { "User-Agent": USER_AGENT },

Ключевой момент именно для WWR (WWR — сокращение WeWorkRemotely, как оно фигурирует в комментариях кода) (см. комментарий в коде, weWorkRemotelyStrategy.ts:107-118): изначально detail-страницы тоже пытались брать через Puppeteer, но при повторных навигациях в одной сессии Cloudflare фингерпринтил браузер и глушил JSON-LD (4 из 5 попыток возвращали страницу без блока, хотя тот же URL руками в браузере открывался нормально). Переход на RSS решил это полностью — фид отдаётся обычным axios без каких-либо челленджей, и одним запросом покрывает сразу все вакансии категории, а не по одному Puppeteer-заходу на вакансию.

То есть: HTML/JSON-LD/RSS — это не про "разные технологии парсинга", а про то, в каком виде и с каким уровнем защиты сайт готов отдавать вам одни и те же данные — и CrawlStrategy просто выбирает самый дешёвый и надёжный канал из доступных для конкретного сайта.

Что такое networkidle2? Что такое fingerprint в смысле блокировки Cloudflare, как его можно "размыть" и какие приёмы применяются в проекте?

networkidle2 — что это и зачем

Это значение опции waitUntil у page.goto() в Puppeteer — критерий, по которому Puppeteer решает, что страница "загрузилась", прежде чем отдать управление обратно коду. Варианты:

ЗначениеКогда считается "готово"
loadСработало событие window.onload (все статические ресурсы получены)
domcontentloadedDOM (Document Object Model — дерево элементов страницы) построен, но картинки/XHR (XMLHttpRequest — фоновый запрос браузера без перезагрузки страницы)/фетчи могут ещё идти
networkidle0Не было ни одного сетевого запроса ≥ 500 мс подряд
networkidle2Не более 2 одновременных запросов в течение ≥ 500 мс подряд

Оба сайта, где применяется Puppeteer, рендерят контент через JS уже после начальной загрузки (SPA-подобное поведение (SPA — Single Page Application, приложение, где контент дорисовывается JS уже после начальной загрузки страницы)) — простого load недостаточно, потому что вакансии могут дорисовываться уже после него отдельными XHR/фетч-запросами. networkidle2 выбран вместо более строгого networkidle0 как компромисс: аналитика/трекеры/long-polling запросы часто никогда полностью не "затихают" (0 активных соединений), так что networkidle0 рискует зависать/таймаутить там, где контент уже фактически готов — вспомогательные фоновые запросы игнорируются, пока их не больше 2 одновременно.

Файл: apps/api/src/crawler/strategies/remoteOkStrategy.ts, строки 172–175

await page.goto(pageUrl, {
  waitUntil: "networkidle2",
  timeout: NAVIGATION_TIMEOUT_MS,
});

Что такое "fingerprint" в контексте блокировки Cloudflare

Fingerprint — это не один конкретный заголовок, а совокупность сигналов, по которым Cloudflare (или другой anti-bot слой) отличает настоящий браузер реального человека от автоматизированного клиента. Условно несколько уровней:

  • Сетевой уровень — TLS (Transport Layer Security — протокол шифрования соединения, тот самый "замочек" в адресной строке)/JA3-отпечаток (JA3 — метод отпечатка клиента по порядку и набору cipher suites при TLS-хендшейке — начальном обмене параметрами шифрования), порядок и состав HTTP-заголовков. У axios/Node.js это совершенно не похоже на отпечаток настоящего Chrome, даже если вручную выставить заголовок User-Agent (UA — строка в заголовке запроса, которой клиент называет себя серверу) равным Chrome — остальной "почерк" запроса всё равно выдаёт не-браузер.
  • JS-окружение — Cloudflare отдаёт JS-челлендж и проверяет, что его исполняет настоящий браузерный движок: наличие navigator.webdriver (по умолчанию true в headless-режимах, если явно не пропатчено), список плагинов, поведение Canvas/WebGL-рендеринга, таймингов выполнения — всё это не подделать одним заголовком, нужен реальный движок рендеринга.
  • Поведенческий/сессионный уровень — даже пройдя первичный челлендж (то есть будучи настоящим headless Chromium с корректным TLS/JS), сессия может быть помечена как автоматизированная по паттерну использования: слишком регулярные интервалы между запросами, последовательные "машинные" переходы без пауз/скролла/мыши, повторные однотипные навигации в одной и той же сессии.

Именно третий уровень — то, что реально произошло на WeWorkRemotely: обычный HTTP-запрос (axios) получает 403 из-за первого, браузерного уровня — это решается Puppeteer'ом. Но при повторных detail-page навигациях в рамках одной и той же Puppeteer-сессии Cloudflare начинал глушить JSON-LD блок уже после первого успешного захода — это как раз поведенческий фингерпринт сессии, а не разовая проверка заголовков.

Файл: apps/api/src/crawler/strategies/weWorkRemotelyStrategy.ts, строки 228–231

title: "PROBLEM - headless session fingerprinted",
explanation: "Only 1/5 detail fetches found a JobPosting block - the other 4 came back with it
silently missing, even though re-opening the same URLs in a real (non-headless) browser

Puppeteer session as automated after its first successful navigation, not a per-vacancy data gap."

Как вообще можно "размыть" fingerprint (общие приёмы, не всё используется в проекте)

  • Реалистичный User-Agent реального десктопного браузера вместо стандартного UA библиотеки/автоматизации.
  • Puppeteer-стелс-плагины (например puppeteer-extra-plugin-stealth) — патчат navigator.webdriver, подделывают список плагинов, WebGL-vendor и другие JS-детекторы headless-режима.
  • Ротация IP/резидентных прокси — чтобы разные запросы не выглядели одной и той же машиной.
  • Рандомизация viewport, таймзоны, языка браузера.
  • Джиттер (случайный разброс) между запросами вместо идеально регулярных интервалов — регулярность сама по себе бот-сигнал.
  • Ограничение переиспользования одной browser-сессии на много навигаций подряд — свежая сессия на каждый заход снижает шанс поведенческой пометки.

Что реально применяется в этом проекте

Проект осознанно не идёт по пути "гонки вооружений" со стелс-плагинами, а там, где это возможно, ищет незащищённый канал вместо того, чтобы взламывать защищённый — тот самый переход на RSS для WWR вместо усиления Puppeteer-обхода. Из реально применённого:

  1. Реалистичный десктопный UA — не дефолтный Puppeteer UA (сам по себе detectable) и не честный "бот"-UA (свёл бы на нет смысл использования настоящего браузера).

Файл: apps/api/src/crawler/strategies/remoteOkStrategy.ts, строки 10–17

// A real desktop Chrome UA, not Puppeteer's default and not any bot-identifying string. RemoteOK
// 403s plain (non-browser) requests via a Cloudflare bot check — Puppeteer exists here to pass as
// a real browser, so presenting a truthful non-browser UA would defeat the point.
const USER_AGENT =
  "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/131.0.0 Safari/537.36";
  1. Джиттер поверх настраиваемой задержки — каждая пауза между запросами к одному источнику получает случайную добавку 0–7с, специально чтобы избежать "миллиметрово-точного" интервала, который сам по себе бот-сигнал.

Файл: apps/api/src/crawler/rateLimiter.ts, строки 7–15

// Added on top of every wait, never subtracted - a perfectly regular request interval is itself
// a bot signal (no real client, automated or human, hits an endpoint at millisecond-perfect
// intervals).
const MAX_JITTER_MS = 7000;

function withJitter(delayMs: number): number {
  return delayMs + Math.floor(Math.random() * (MAX_JITTER_MS + 1));
}
  1. Один запуск браузера на один прогон, а не переиспользование одного и того же browser/page на множество навигаций подряд — снижает поведенческую "плотность" одной сессии (хотя, как показал случай WWR, этого недостаточно против сессионного фингерпринтинга при множественных detail-переходах).
  1. Сознательно НЕ применены стелс-плагины/подмена navigator.webdriver и прочие JS-патчи — задокументировано как рассмотренная, но отклонённая альтернатива: вместо того чтобы глубже прятать автоматизацию, для WWR был найден легитимный канал (RSS), не защищённый Cloudflare вообще.

Файл: apps/api/src/crawler/strategies/weWorkRemotelyStrategy.ts, строка 108

// resilient (stealth plugins, longer delays, etc. - left as documented alternatives, not applied).

Итог: вместо эскалации в сторону всё более изощрённого сокрытия автоматизации, проект следует принципу "вежливости by design" — реалистичный UA и джиттер снимают базовую детекцию там, где Puppeteer необходим, а там, где протокол сайта сам предлагает менее защищённый машиночитаемый канал (JSON-LD в листинге RemoteOK, RSS-фид WWR), используется он вместо более агрессивного обхода защиты.

Что такое поле steps у CrawlStrategy и как работает StrategyFlow?

Это не какой-то библиотечный паттерн — это собственная (bespoke) конвенция проекта: обычный TypeScript-объект, реализующий интерфейс CrawlStrategy, где поле steps описывает "историю" функции crawl()/enrichDetails() как данные, а не как прозу в комментарии.

Это существует только ради UI-диаграммы

Массив steps не влияет на реальное исполнение краулинга — движок не читает его и не выполняет по нему шаги. Это чисто описательные данные "для человека": автор стратегии пишет их вручную рядом с реальным кодом (в том же файле, часто в том же коммите), они отдаются через API на фронтенд и рендерятся компонентом StrategyFlow как визуальная блок-схема на странице источника — кликабельная, с раскрывающимися деталями по шагам.

Смысл решения (см. комментарий у самого поля, types.ts:62-68): раз диаграмма — это просто ещё одно поле в том же объекте, что и сам код, менять код без обновления диаграммы неудобно ровно настолько, насколько неудобно забыть обновить соседнее поле в одном и том же объекте. Классическая проблема "документация/диаграмма устарела, а код уже другой" таким образом устраняется структурно, а не дисциплиной автора.

Формат одного шага

Файл: apps/api/src/crawler/types.ts, строки 31–49

export type StrategyStepType = "process" | "decision" | "problem" | "solution" | "terminal";

export interface StrategyStep {
  type: StrategyStepType;
  title: string;               // всегда видно
  detail?: {
    method?: string;           // конкретный вызов библиотеки, если есть
    explanation: string;       // что и почему
    result?: string;           // измеренный результат, если есть
  };
}

type — закрытый union из 5 вариантов, и именно он определяет, как шаг отрисуется:

typeКак выглядит в UIСмысл
processОбычный прямоугольник"что делается сейчас", например "Fetch listing via Axios"
decisionПунктирная "таблетка", курсивомРазвилка вида "Blocked (403)? → Yes."
problemПодсвечен как ошибка (красная рамка/текст)"вот тут всё сломалось"
solutionЖирный текст"вот чем починили"
terminalПунктирный, приглушённыйКонечная точка цепочки

detail — опционален; если есть, в UI по клику раскрывается блок с method/explanation/result. Если detail нет — кнопка неактивна, просто заголовок без возможности раскрыть.

Как это рендерится

Файл: apps/web/entities/source/ui/strategy-flow.tsx

export function StrategyFlow({ steps }: { steps: StrategyStep[] }) {
  return (
    <div className="flex flex-col items-stretch gap-1.5">
      {steps.map((step, index) => (
        <div key={index} className="flex flex-col items-center gap-1.5">
          <StepBox step={step} />
          {index < steps.length - 1 && <span>{"↓"}</span>}
        </div>
      ))}
    </div>
  );
}

Просто маппит массив steps в вертикальную цепочку блоков со стрелками ↓ между ними — тот самый "flowchart". StepBox внутри выбирает CSS-классы/форму по step.type и управляет раскрытием detail через useState.

Есть ещё одна деталь — глоссарий: в строках title/explanation/ result можно писать {{term}} (например {{cf-mitigated}}), и renderWithGlossary() превращает такой токен во всплывающую подсказку с определением из STRATEGY_GLOSSARY — так термины объясняются прямо в UI, без ухода на другую страницу.

Изменение для демонстрации: детали раскрыты по умолчанию

До этого изменения каждый шаг рендерился свёрнутым (useState(false)) — на презентации пришлось бы кликать по каждому шагу, чтобы показать его detail. Добавлен проп defaultExpanded у StrategyFlow/StepBox: при defaultExpanded все шаги сразу открыты, но каждый по-прежнему можно свернуть кликом индивидуально — меняется только начальное состояние, не поведение.

04 · "Did you use mapping?" (слайд презентации — детальный разбор)

Кикер слайда — реальный вопрос, который задают на собеседовании/ревью, и слайд специально показывает, что в нём на самом деле два разных вопроса, спрятанных за одним словом "mapping". Это тот же материал, что и в самой первой главе этого документа ("Что такое ETL-mapping"), но здесь — ровно в том виде и структуре, в которой это подаётся на слайде.

ETL mappingстадия 02 — внутри каждой CrawlStrategy

Словарь каждого источника переводится в RawVacancy уже во время парсинга, по-своему для каждого сайта: 

hiringOrganization.name             → company
jobLocationType === "TELECOMMUTE"   → isRemote

Сводит четыре разных "словаря" источников в одну форму — до того, как что-либо коснётся базы.

Elasticsearch mappingстадия 04 — схема индекса

Буквальный ES-термин: типы полей, keyword vs text под-поля для фасетов и автокомплита.

Версионируется через CRAWLER_RESULTS_SCHEMA_VERSION — несовместимое изменение пересобирает индекс целиком, а не мигрирует на месте, поскольку это производный кэш.

Этот mapping в буквальном смысле определяется в момент upsert'а.

Так какой из двух имелся в виду? Формулировка "mapping данных из источников" читается как ETL-смысл — который происходит раньше, по каждому источнику отдельно, а не в момент записи. Оба значения реально существуют в системе; точный ответ называет оба и указывает, где живёт каждый.

05 · Under the hood (слайд презентации — детальный разбор)

Слайд показывает, что реально пишется одним upsert-запросом в Elasticsearch — конец цепочки "стадия 02" (ETL mapping) и начало "стадии 04" (ES mapping) с предыдущего слайда, соединённые в одном реальном документе.

Файл: apps/api/src/search/upsertVacancy.ts, строки 11–54

const id = `${raw.sourceId}:${raw.externalId}`;   // ключ дедупликации

const detailFields = {
  ...(raw.description !== undefined ? { description: raw.description } : {}),
  ...(raw.location !== undefined ? { location: raw.location } : {}),
  ...(raw.isRemote !== undefined ? { isRemote: raw.isRemote } : {}),
  // ...
};

await esClient.update({
  index: CRAWLER_RESULTS_INDEX,
  id,
  doc: { sourceId: raw.sourceId, externalId: raw.externalId, title: raw.title, /* ... */ lastSeenAt: now, ...detailFields },
  upsert: { /* то же самое + firstSeenAt: now */ },
});

Ключевые детали, которые слайд подсвечивает построчно на примере документа:

  • Ключ дедупликации — sourceId:externalId, не сам ES _id из базы и не listingId. Повторный краулинг того же источника обновляет lastSeenAt, а не создаёт дубль.
  • isRemote: undefined — намеренно пропущено, а не записано как false. Спред ...(raw.isRemote !== undefined ? {...} : {}) гарантирует: если источник не дал сигнала про remote/on-site, поле в документе просто отсутствует, а не лжёт значением "не удалённая работа". Тот же принцип виден в комментарии у habrCareerStrategy.ts:96-100 про "отсутствие данных ≠ null-значение поля".
  • listingId — только атрибуция, не ключ дедупликации. Если одна и та же вакансия попадается в нескольких листингах источника (например, разные города Craigslist), записывается тот listingId, который обновил документ последним — это best-effort-поле, а не часть идентичности вакансии.
  • Типы полей под конкретную задачу (это и есть буквальный "Elasticsearch mapping"): title/company — text с суб-полем .suggest (нормализованный в lowercase keyword, специально для автокомплита); company/location дополнительно несут .keyword для facet-агрегаций — обычный text агрегировать напрямую нельзя.

Файл: apps/api/src/search/crawlerResultsIndex.ts, строки 63–81

title: {
  type: "text",
  fields: { suggest: { type: "keyword", normalizer: "lowercase_normalizer" } },
},
company: {
  type: "text",
  fields: {
    keyword: { type: "keyword" },
    suggest: { type: "keyword", normalizer: "lowercase_normalizer" },
  },
},

.keyword и .suggest — два разных суб-поля с разным назначением, и это не случайность: company.keyword должен остаться оригинального регистра, потому что именно он управляет точным фильтром/отображением в facet "Company"; лишь отдельное .suggest-поле нормализуется в lowercase — иначе автокомплит и facet конфликтовали бы за одно и то же значение.

06 · Why build this (слайд презентации — детальный разбор)

Закрывающий слайд — четыре итоговых тезиса, каждый — прямое следствие одной из глав выше.

  1. Одна абстракция, четыре структурно разных сайта. Интерфейс CrawlStrategy ни разу не поменялся между static HTML, Cloudflare-gated JS, RSS и scoped-classifieds-сайтом — это и есть глава "03 · Four Sources, Four Problems" выше.
  2. Реальные anti-bot проблемы, реальные фиксы. Живой случай фингерпринтинга Cloudflare заставил на ходу перейти на RSS — задокументировано по факту произошедшего, а не придумано заранее. Это глава про networkidle2/fingerprint/RSS выше.
  3. Поисковый слой, ведущий себя как в production. Faceted-фильтрация, автокомплит, подсветка совпадений, пересобираемый индекс — это как раз то, что описано в главе "05 · Under the hood" про .keyword/.suggest-суб-поля и CRAWLER_RESULTS_SCHEMA_VERSION.
  4. Вежливость by design. Каждый источник рейт-лимитится с джиттером и кэшируется — demo- скрапер всё равно остаётся скрапером. Это глава про джиттер в rateLimiter.ts выше.

По сути этот слайд — не новая информация, а явная сшивка четырёх более ранних технических глав в один связный вывод: "то, что мы построили, реально работает как маленькая, но настоящая production data-ingestion система, а не только как демо для одного конкретного сайта".
